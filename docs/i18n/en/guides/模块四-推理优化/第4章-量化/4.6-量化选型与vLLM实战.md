Methods are covered. Back to a concrete deployment question: you have one model and one GPU, which quantization do you try first? It is a bit like seeing a doctor: **find the worst symptom first (the tightest constraint), rule out treatments the body cannot take (paths the hardware and backend do not support), then confirm the effect with test results (quality and performance evals).** This section builds a candidate order first, then compares FP16 and AWQ INT4 on vLLM.

> ⏰ **Currency:** vLLM quantization entry points, scheme names, and Kernel selection are based on v0.32.0 (released 2026-10-18). Quantization support matrices move fast; after a version change, re-check the docs and the startup logs.

## 1. Pick candidates from the bottleneck

The figure below is the selection flow: first enter one of the blue, yellow, or green candidate branches by the tightest constraint, then compare quality against a 16-bit baseline for all of them; green boxes mean compare performance once quality passes, red boxes mean adjust when it fails, then return to quality eval:

![Quantization selection flow: confirm compatibility and find the tightest constraint, pick candidates by weight, KV, or compute bottleneck, compare quality against an FP16/BF16 baseline, then compare latency and throughput if it passes, or adjust and re-eval if it fails](../../../../../../public/images/quantization/quant-selection-flow.svg)

Branches can be combined. When weights do not fit and the long-context cache is also short, validate INT4 weights first, then stack FP8 KV Cache, and eval once after each addition.

| 📊 Primary constraint | Prefer first | What to confirm next |
|---|---|---|
| Low tolerance for quality drop | Keep FP16/BF16 as baseline, try 8-bit first (FP8 or INT8 W8A8) | Target-task quality; 8-bit may still miss the bar |
| Weights do not fit, small-Batch weight reads are slow | GPTQ/AWQ INT4 (W4A16) | Group Size, actual Kernel, sensitive layers |
| Long context or concurrency limited by KV | FP8 KV Cache | Whether Scale is calibrated, Attention backend, long-text quality |
| GEMM compute dominates | Hardware-supported W8A8; on Blackwell, evaluate NVFP4 | Actual op path and end-to-end gains |

Hardware filters some candidates first. Per the vLLM v0.32.0 docs: FP8 compute needs compute capability 8.9+, and Ampere can only take W8A16; INT8 W8A8 supports Turing through Hopper and **does not support Blackwell**; native NVFP4 compute needs Blackwell, and other GPUs fall back to Marlin W4A16.

When you do not have a quantized checkpoint yet, generate one offline first:

- **LLM Compressor**: maintained by the vLLM project; covers GPTQ, AWQ, SmoothQuant, FP8, and KV Cache Scale calibration, and exports `compressed-tensors`.
- **GPTQModel**: focused on the GPTQ family.
- **NVIDIA Model Optimizer**: exports ModelOpt formats such as FP8, NVFP4, and MXFP8.

Calibration and export are a separate workflow. This section's main experiment uses published checkpoints so we can focus on deployment effects.

## 2. How vLLM recognizes a quantized model

### 2.1 Keep method, format, and Kernel separate

| 📊 Name | Which layer | What loading looks at |
|---|---|---|
| GPTQ, AWQ | Quantization algorithm and its common checkpoint format | Bit width, Group Size, zero-point, weight packing |
| `compressed-tensors` | A format and config system that can carry several schemes | May actually be INT8, INT4, FP8, and so on |
| FP8, NVFP4, MXFP4 | Numeric format and the matching scale scheme | Checkpoint config, hardware, backend |
| Marlin, Machete, CUTLASS, etc. | Execution Kernel | Whether it matches the weight layout and device |

vLLM reads `quant_method` from the checkpoint config and usually does not need `--quantization`. In v0.32.0 method names and Kernels are decoupled: `awq`, `awq_marlin`, and `auto_awq` all resolve to the same `auto_awq` config, and GPTQ works the same way; the concrete Kernel is picked by priority (section 4.3). So **whether you pass `--quantization` or not, check the startup logs for the actual Kernel**, for example `Using MarlinLinearKernel for AutoAWQMarlinLinearMethod`, or `Selected <kernel> for <module>` on FP8 layers.

### 2.2 What different entry points mean

The commands below are different config entry points; start only one at a time, and replace local paths with your exported checkpoints:

```bash
# Existing AWQ checkpoint: config identifies bit width, Kernel is chosen automatically
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --dtype half

# Existing compressed-tensors checkpoint (exported by LLM Compressor): config identifies the concrete scheme
vllm serve /path/to/compressed-tensors-model

# Existing ModelOpt NVFP4 checkpoint
vllm serve /path/to/nvfp4-model --quantization modelopt_fp4

# Online FP8: convert BF16/FP16 weights to FP8 at load time, no calibration data needed
vllm serve Qwen/Qwen2.5-7B-Instruct --quantization fp8_per_tensor
```

Online quantization currently offers schemes such as `fp8_per_tensor`, `fp8_per_channel`, `fp8_per_block`, `mxfp8`, and `mxfp4` (format details in section 4.5); activations get a dynamic Scale on every forward. The docs note that `fp8_per_tensor` has limited latency gains and is better for a quick try; for performance and quality, use an offline-calibrated checkpoint.

⚠️ **Note:** The old online form `--quantization fp8` is no longer supported in v0.32.0; using it on an unquantized checkpoint errors and tells you to switch to `fp8_per_tensor`. `fp8` can still load checkpoints that are already FP8.

Online conversion happens at load time. Online FP8 in v0.32.0 first builds the original-precision weights on a meta device (shape only, no GPU memory), then converts each linear layer's weights to FP8 as soon as they load, so the full 16-bit weights are never in GPU memory at once. It still reads the original-precision checkpoint and does not get offline calibration, so for production prefer an offline-quantized checkpoint.

## 3. Start FP16 and AWQ servers

Run the FP16 baseline on the original model first:

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --served-model-name quant-demo \
    --dtype half \
    --max-model-len 4096 \
    --max-num-seqs 32 \
    --gpu-memory-utilization 0.9 \
    --generation-config vllm \
    --no-enable-prefix-caching
```

Send a few requests, save the logs, stop the process, confirm GPU memory is free, then start AWQ:

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ \
    --served-model-name quant-demo \
    --dtype half \
    --max-model-len 4096 \
    --max-num-seqs 32 \
    --gpu-memory-utilization 0.9 \
    --generation-config vllm \
    --no-enable-prefix-caching
```

Keep the same activation type, context limit, concurrency limit, and cache precision on both sides, and pass no `--quantization`; the checkpoint config decides. The original Qwen checkpoint ships as BF16; we unify on FP16 here so it lines up with AWQ's FP16 activation path (see the [AWQ model card](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-AWQ)).

On every start, record three things: model weight footprint, available KV Token capacity, and the actual quantization Kernel. The weight space AWQ frees is given to the KV Cache by vLLM, so total usage in `nvidia-smi` will not shrink to a quarter; what changes is KV capacity.

## 4. Measure offline throughput with controlled variables

### 4.1 Answer one bounded question first

The experiment below only answers: **with the same input Tokens, a fixed output length, and the same engine config, how fast does a batch of requests finish?** It does not give online TTFT/TPOT tail latency, and it does not stand in for service behavior under a real arrival rate.

Stop the online server above, save the code below as `compare_quant.py`. The script loads one model at a time, warms up, then measures three rounds, saving output Token/s, total Token/s, and generation samples. Both models build inputs with the same Tokenizer; Prefix Cache is off during the throughput phase, and EOS is ignored so the output volume stays fixed.

```python
import argparse
import json
import statistics
import time
from pathlib import Path

from transformers import AutoTokenizer
from vllm import LLM, SamplingParams


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--model", required=True)
    parser.add_argument("--tokenizer", default="Qwen/Qwen2.5-7B-Instruct")
    parser.add_argument("--quantization", default=None)
    parser.add_argument("--num-prompts", type=int, default=64)
    parser.add_argument("--input-len", type=int, default=512)
    parser.add_argument("--output-len", type=int, default=256)
    parser.add_argument("--save", required=True)
    args = parser.parse_args()
    if min(args.num_prompts, args.input_len, args.output_len) <= 0:
        parser.error("Request count and token lengths must be positive")
    if args.input_len + args.output_len > 4096:
        parser.error("Input plus output cannot exceed this experiment's 4096 token limit")

    tokenizer = AutoTokenizer.from_pretrained(args.tokenizer)
    # Build repeatable fixed-length inputs. This batch is for speed only, not quality eval.
    prompts = []
    for i in range(args.num_prompts):
        unit = tokenizer.encode(
            f"Request id {i}. Explain how quantization affects inference memory and compute.",
            add_special_tokens=False,
        )
        ids = (unit * (args.input_len // len(unit) + 1))[:args.input_len]
        prompts.append({"prompt_token_ids": ids})

    llm = LLM(
        model=args.model,
        tokenizer=args.tokenizer,
        quantization=args.quantization,
        dtype="half",
        max_model_len=4096,
        max_num_seqs=32,
        max_num_batched_tokens=2048,
        gpu_memory_utilization=0.9,
        kv_cache_dtype="auto",
        enable_prefix_caching=False,
        generation_config="vllm",
        seed=0,
    )
    params = SamplingParams(
        temperature=0, max_tokens=args.output_len, ignore_eos=True, seed=0
    )
    llm.generate(prompts, params, use_tqdm=False)  # Full-load warmup, not timed
    measurements = []
    for _ in range(3):
        start = time.perf_counter()
        outputs = llm.generate(prompts, params, use_tqdm=False)
        elapsed = time.perf_counter() - start
        output_tokens = sum(len(o.outputs[0].token_ids) for o in outputs)
        expected = args.num_prompts * args.output_len
        if output_tokens != expected:
            raise RuntimeError(f"Got {output_tokens} output tokens, expected {expected}")
        input_tokens = sum(len(o.prompt_token_ids) for o in outputs)
        measurements.append({
            "seconds": elapsed,
            "output_tokens_per_second": output_tokens / elapsed,
            "total_tokens_per_second": (input_tokens + output_tokens) / elapsed,
        })

    # Quality samples restore normal EOS and use a consistent Chat Template; not part of throughput timing.
    questions = [
        "Return JSON only: name is Alice, count is the integer 3, no Markdown fences.",
        "There are 17 boxes of goods, 24 items each. After shipping 89 items, how many remain? Show the calculation.",
        "Write a Python function that checks whether a string is a palindrome, ignoring case and non-alphanumeric characters.",
    ]
    chats = [[{"role": "user", "content": q}] for q in questions]
    texts = [tokenizer.apply_chat_template(
        chat, tokenize=False, add_generation_prompt=True
    ) for chat in chats]
    examples = llm.generate(
        texts, SamplingParams(temperature=0, max_tokens=512, seed=0),
        use_tqdm=False,
    )
    result = {
        "config": vars(args),
        "runs": measurements,
        "median_output_tokens_per_second": statistics.median(
            r["output_tokens_per_second"] for r in measurements
        ),
        "examples": [
            {"question": q, "answer": o.outputs[0].text}
            for q, o in zip(questions, examples)
        ],
    }
    Path(args.save).write_text(
        json.dumps(result, ensure_ascii=False, indent=2), encoding="utf-8"
    )
    print(json.dumps(result, ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()
```

### 4.2 Run the two processes separately

```bash
python compare_quant.py \
    --model Qwen/Qwen2.5-7B-Instruct \
    --save fp16.json

python compare_quant.py \
    --model Qwen/Qwen2.5-7B-Instruct-AWQ \
    --save awq-int4.json
```

Finish the first before starting the second so the two engines do not fight for GPU memory. Each side submits 64 requests, 512 input and 256 output Tokens each, with an engine concurrency cap of 32 sequences. For a small-Batch case, add `--num-prompts 1 --input-len 64` to both commands and save the results separately.

Timing wraps the whole blocking `generate()` call, including local scheduling and output packing; model download, load, and the first warmup are excluded. For a serious comparison, keep GPU idle state consistent, alternate the two configs, and watch for variance; use profiling tools when you need operator-level timing.

## 5. How to compare generation quality

The three questions in the script are only a smoke check for obvious drops in format, arithmetic, and coding ability:

| 📊 Sample | How to check |
|---|---|
| JSON output | Parses as an object, fields and values are correct, `count` is an integer |
| Arithmetic | Should get $17\times24-89=319$, with matching steps and answer |
| Palindrome function | Test with the empty string, `A man, a plan, a canal: Panama`, `ab`, and similar inputs |

Byte-for-byte different outputs are not the same as a quality drop. Even at temperature 0, different numeric paths do not guarantee identical text; score against the task requirements and track pass-rate changes.

Formal eval should be independent of the calibration set and cover real workloads: Chinese instructions, code, math, structured output, long-document QA, and so on. Fix the Prompt, Chat Template, max generation length, and scoring rules, then compare the baseline and the quantized model. PPL can be a supplement, but it does not replace code accuracy or retrieval accuracy.

When one task class drops clearly, first check the template, truncation, and quantization config; after the eval itself is consistent, consider finer granularity, keeping sensitive layers at higher precision, raising bit width, or recalibrating. Only when PTQ still misses the bar and you have training capacity should you consider QAT.

## 6. Reading results and common issues

Fold the two JSON files and the startup logs into the table below. Leave unrun rows blank; do not fill them with paper numbers or results from other hardware:

| 📊 Metric | FP16 baseline | AWQ INT4 |
|---|---|---|
| Model revision / vLLM / GPU | To record | To record |
| Actual quantization Kernel | N/A | To record |
| Model weight footprint / KV Token capacity | To record | To record |
| Median output Token/s (3 runs) | To measure | To measure |
| Total Token/s and input/output lengths | To measure | To measure |
| Task pass rate / failing samples | To eval | To eval |

The ratio of output Token/s can stand in for the speedup under this fixed load. Total throughput that includes input Tokens should be listed separately; do not mix the two definitions.

| 📊 Symptom | Check first |
|---|---|
| AWQ checkpoint will not load | Whether it is a real AWQ checkpoint, and whether config and tool versions match |
| INT4 fits but is slower than FP16 | Actual Kernel in the logs, any "Falling back to unoptimized AWQ kernels" fallback, matrix shapes, and the current bottleneck |
| Total GPU memory barely drops | Whether the KV pool absorbed the freed weight space; check KV Token capacity |
| Fast on small Batch, little gain on large Batch | Whether GEMM has already shifted to compute-bound (section 4.3) |
| Long-text quality drops | KV precision, whether Scale is calibrated, truncation length, long-text eval coverage |
| NVFP4 model did not get faster | Whether the GPU has a native FP4 Kernel, and whether logs show a Marlin W4A16 fallback |

💡 **Tip:** To exclude a Kernel for an ablation, use the `VLLM_DISABLED_KERNELS` environment variable; for NVFP4 and similar formats you can pin the linear-layer backend with `--linear-backend`.

If the FP16 baseline cannot run on the current device, record the capacity limit as is. You can shrink the shared load, or redo the comparison on a machine with enough memory. Running only the quantized model shows deployment is possible, but it does not tell you how much faster it is than FP16.

## 📝 Summary

- Start from weight, KV, or compute bottlenecks to pick candidates, then drop unsupported paths by hardware: FP8 compute needs CC 8.9+, INT8 W8A8 does not support Blackwell, native NVFP4 compute needs Blackwell.
- Quantization algorithm, checkpoint format, numeric format, and execution Kernel are four different things; vLLM v0.32.0 auto-detects the scheme from the checkpoint and picks a Kernel by priority, so trust the startup logs.
- Online quantization uses scheme names such as `fp8_per_tensor`, `fp8_per_block`, `mxfp8`, and `mxfp4`; the old online `--quantization fp8` form is no longer supported.
- Controlled experiments must fix model source, input/output lengths, engine config, and measurement definition, and change only one variable at a time.
- Quantization is worth it when quality and latency still pass, in exchange for memory or throughput gains.
