In real workloads, huge numbers of requests share the same opening: the same few-hundred-token system prompt, the same few-shot examples, or the repeated history in a multi-turn chat. Prefilling that shared prefix from scratch on every request is a huge waste. Prefix Cache keeps the KV Cache for that shared prefix and lets later requests reuse it. This section covers how vLLM's hash-based automatic prefix caching works, and how SGLang's RadixAttention builds on the idea.

> ⏰ **Currency note**: the RadixAttention material follows the SGLang paper; vLLM's hash algorithm, default switches, and source walk-through are based on v0.32.0 (released 2026-10-18).

## 1. How wasteful repeated prefixes are

A few everyday cases:

- **Shared system prompt**: a customer-service bot puts an 800-token role and rule sheet in front of every request; only the user's sentence changes.
- **Few-shot prompts**: every classification request carries the same 10 examples, so a few thousand example tokens are identical across requests.
- **Multi-turn chat**: turn 5's input is the full history of the first 4 turns plus the new question, so the first 4 turns overlap heavily with turn 4's request.

What they share: **large stretches of tokens are identical across requests, and they sit in the same place (at the start of the sequence)**. As the last chapter covered, Prefill is compute-bound heavy work. Prefilling the same 800-token prefix on every request means repeating the same expensive compute over and over.

📌 **Key point**: Attention causality means **a token's Key/Value depends only on that token and the tokens before it**. So if two requests have **exactly the same prefix**, every token in that prefix produces the same KV, and you can compute it once and share it.

Analogy: a standard contract where the first few pages of boilerplate are the same for every customer. You do not redraft those pages each time; keep one template and fill in only the personalized clauses at the end.

## 2. The physical basis for reuse: block-level KV sharing

Prefix reuse needs GPU memory management that lets multiple requests point at the same KV. That is the foundation PagedAttention laid in the previous section:

- The KV Cache is stored in **fixed-size blocks**; requests reference physical blocks indirectly through a block table.
- When some prefix blocks of two requests have the same content, their block tables **point at the same physical block**, and a **reference count** tracks how many requests use it.
- Newly generated content goes into each request's own new blocks; shared blocks are read-only. vLLM V1 only shares fully written blocks, so cross-request reuse never writes into a shared block and does not need Copy-on-Write.

So Prefix Cache is really **taking "share prefix blocks among concurrent requests" and extending it to "reuse them across requests that arrive one after another"**: keep the prefix blocks a finished request computed instead of dropping them right away; if a later request's prefix matches, reuse those blocks and skip the matching Prefill work.

🔑 **Core idea**: **Prefix Cache = reuse prefix KV blocks across requests and across time.** PagedAttention's block sharing is the spatial dimension (concurrent requests share); Prefix Cache extends it into the time dimension (later requests reuse earlier ones).

## 3. vLLM's Automatic Prefix Caching

vLLM's scheme is **Automatic Prefix Caching (APC)**. "Automatic" is a big part of the pitch: **you do not manually mark which span is a shared prefix; the engine detects and reuses it**. It does that by hashing KV blocks.

### 3.1 Block hashes: deciding that a "prefix matches"

The hard question: how do you quickly tell that a prefix block of a new request matches a cached block? vLLM hashes every **full block**. That hash has three parts:

- **The parent block's hash** (i.e. the hash of all earlier prefix blocks)
- **The token sequence inside this block**
- **Extra identifiers** (LoRA ID, multimodal input hash, cache salt, and so on)

$$
\text{block\_hash} = \text{Hash}(\text{parent\_hash},\ \text{block\_tokens},\ \text{extra})
$$

Folding in the parent hash is the important part: it guarantees **the hashes match only when the entire prefix from the start of the sequence through the current block is identical**. That is exactly "same prefix": if block 3's hashes match, all tokens in the first 3 blocks match. Hashing the tokens inside the block itself lowers the chance of collisions.

The figure below walks through the hash chain for two requests with `block_size = 4`. Blue blocks are the system prompt shared by A and B; yellow is A's question; green is B's question. Hashes A computes block by block are registered in the yellow cache table in the middle; blue labels under B mark hits that reuse blocks, red labels mark where content diverges from A starting at block 3 so the hash forks and new Prefill is needed; hatched cells are unwritten slots in a tail block, and incomplete tail blocks are not hashed.

💡 **Tip**: since v0.11, vLLM defaults to `sha256` as the hash algorithm; you can switch with `--prefix-caching-hash-algo` to `sha256_cbor` (reproducible across languages), `xxhash`, `xxhash_cbor`, and others. Non-cryptographic algorithms such as xxhash are faster but have a slightly higher collision risk.

### 3.2 Matching and reuse flow

When a new request arrives, vLLM hashes its prefix block by block and looks each hash up in the cache table (hash → block ID):

- **Hit**: the physical block is still cached; point the request's block table at it, bump the reference count, and **skip Prefill for that part**.
- **Miss**: run normal Prefill, then register the new block's hash in the cache for later requests.

In the figure below, blue cards are the hit branch and red cards the miss branch; after a hit it continues to the next block, and the first miss switches into normal Prefill.

<img src="/AIInfraGuide/images/inference-engine/prefix-cache-lookup-flow.svg" alt="Prefix cache lookup flow: hash each block in the chain and look it up; on a hit, point the block table at the existing physical block, increment ref, skip Prefill, and continue; on a miss, Prefill from that block onward and register new hashes" style="max-width: 100%; display: block; margin: 0 auto;" />

📌 **Key point**: a prefix-cache hit **cuts that Prefill compute entirely**. The most direct win is a **much lower TTFT** (the first token shows up sooner), and the freed compute can serve more requests. Longer shared prefixes and higher hit rates mean larger gains.

### 3.3 V1's "near-zero overhead" design

In earlier versions (V0), prefix caching was off by default because the CPU bookkeeping was not worth it when hit rates were low. The vLLM **V1 engine** rewrote this: all blocks are preallocated into a block pool at init, and embedded doubly linked list pointers inside blocks give O(1) moves and eviction, so bookkeeping cost is tiny. The official design docs call prefix caching "almost a free lunch"; the V1 release blog reports that even at a 0% hit rate, throughput drops by less than 1%. So **in V1, prefix caching is on by default**.

## 4. Cache eviction: LRU and reference counting

Cache space is finite; when physical blocks run out you have to evict old ones. vLLM combines **reference counting** and **LRU (least recently used)**:

- **Blocks in use cannot be evicted**: blocks with reference count > 0 (still used by a request) are protected.
- **Free blocks are evicted by LRU**: when a request finishes, its blocks' reference counts hit zero and they enter the free queue, but **content and hashes are kept for now**—a matching new request that arrives soon can still hit. Only when memory is tight do you actually reclaim the free blocks that have gone unused the longest.

One neat detail: when vLLM frees blocks, it appends the request's blocks to the free-queue tail **in reverse order**. The request's **last block** hashes the most tokens (longest prefix) and is least likely to be reused by another request, so it should be **evicted first**; earlier blocks (short prefixes such as the start of a shared system prompt) are more reusable and stay longer.

💡 **Tip**: reverse-order enqueue encodes a simple intuition—**prefixes closer to the start of the sequence are more general and worth keeping**; later prefixes are more personalized and hard to hit.

## 5. SGLang's RadixAttention

vLLM's hash scheme is efficient, but it has an implicit limit: **matching is block-aligned and along a linear prefix**—it compares one prefix that starts from the beginning, at block boundaries. In multi-turn chat, tree sampling, and similar cases, sharing is **tree-shaped**: one common prefix forks into different continuations.

SGLang's **RadixAttention** manages KV Cache reuse with a **Radix Tree** (compressed prefix tree):

- Each edge is a token sequence; the path from the root to a node is a prefix and maps to cached KV.
- On a new request, walk the tree for **longest-prefix match**; reuse KV for the matched path and compute only after the fork.
- Forks map naturally to "shared prefix + different continuation," which fits multi-turn chat (one history spawning many turns) and parallel sampling (one prompt, many answers).
- Each node has a **reference count** of running requests that use it; only nodes with reference count 0 can be evicted. Eviction is LRU and **evicts leaves first**, so common prefixes on ancestors last longer.
- Scheduling prefers requests that share the longest cached prefix (the paper calls this cache-aware scheduling), which raises hit rate for a given cache capacity.

The figure below is a snapshot of a cache tree. Solid blue nodes are referenced by running requests (ref > 0) and cannot be evicted; the thick green path is the longest match for a new request along "system prompt S → Q1 + A1", so it only Prefills the new green hatched branch Q3; the gray dashed leaf Y has ref = 0 and is the first LRU eviction candidate.

<img src="/AIInfraGuide/images/inference-engine/radix-tree-prefix-sharing.svg" alt="RadixAttention radix-tree example: a new request longest-prefix-matches root → system prompt S → Q1 + A1 and only Prefills the new branch Q3; leaf Y with ref 0 is evicted first" style="max-width: 100%; display: block; margin: 0 auto;" />

| 📊 Dimension | vLLM Automatic Prefix Caching | SGLang RadixAttention |
|---|---|---|
| Data structure | Hash table (block hash → block ID) | Radix Tree (compressed prefix tree) |
| Matching | Block-aligned prefix hash match | Longest-prefix match on the tree (the paper's implementation uses one token per page) |
| Best fit | General shared prefixes (system prompt, few-shot) | Tree-shaped sharing (multi-turn chat, tree sampling) |
| Eviction | LRU + reference counting | LRU + reference counting, leaves first |

🔑 **Core idea**: both aim at the same thing—**reuse shared-prefix KV and skip repeated Prefill**; the difference is the data structure. A hash table is simple and efficient for linear prefixes; a Radix Tree is better at expressing and using tree-shaped prefix sharing.

⚠️ **Note**: do not treat them as opposites. vLLM's scheme is already enough for most workloads, and V1 pushed its overhead near zero; RadixAttention shows extra gains on **heavily tree-shaped reuse** (complex agents, lots of parallel sampling). The SGLang paper reports up to 6.4× throughput on such structured LLM-program workloads; that number comes from RadixAttention combined with other optimizations. Choose by your traffic shape, not by assuming "trees always beat hashes."

## 6. Source walk-through: hashing and matching in vLLM APC

That was the idea; now into vLLM V1 source to see how the hash chain and block reuse actually land. Most of the logic lives in `vllm/v1/core/kv_cache_utils.py` (hashing) and `block_pool.py` / `kv_cache_manager.py` (reuse and eviction). The walk-through follows the main-branch design docs; the code keeps moving, so treat your installed version as the source of truth.

### 6.1 How block hashes form a chain

The "parent hash" from §3.1 is implemented by **chaining blocks one after another**. The hash of each **full block** is the hash of a tuple with three things:

- **The parent block's hash** (the previous block's `block_hash`; the first block's parent is a constant `NONE_HASH`)
- **This block's token tuple** (lowers collision chance)
- **Extra discriminators** (LoRA ID, multimodal input hash, `cache_salt`, etc.; `cache_salt` is attached only to the first block, because the parent hash carries it down the chain to every later block)

```python
# Pseudocode: reconstructs vLLM's chained block-hash computation (not literal source)
# When PYTHONHASHSEED is set it is derived from that; otherwise sha256-family uses a fixed seed, xxhash-family a random one
NONE_HASH = <constant fixed at process start>

def hash_request_tokens(token_ids, block_size, extra):
    block_hashes = []
    parent_hash = NONE_HASH                       # first block has no parent
    for blk_tokens in chunk(token_ids, block_size):
        if len(blk_tokens) < block_size:
            break                                 # hash only "full blocks"
        # Key: fold in the parent hash → naturally encodes "the whole prefix from the start to here"
        curr_hash = hash((parent_hash, tuple(blk_tokens), extra))
        block_hashes.append(curr_hash)
        parent_hash = curr_hash                   # advance the chain
    return block_hashes
```

🔑 **Core idea**: **chaining parent hashes makes the hash of the $k$-th block uniquely encode "all tokens in the first $k$ blocks of the sequence."** So "two requests have the same hash at block $k$" $\Leftrightarrow$ "their first $k$ blocks' tokens are identical"—prefix matching collapses to one hash table lookup, an $O(1)$ check.

💡 **Tip**: only **full blocks** are cached (in source, a tail shorter than `block_size` is not hashed). That is why prefix hits are always "block-aligned"—a leftover shorter than one block cannot be reused.

### 6.2 Four tables for reuse and eviction

At init, `BlockPool` builds several structures that work together (echoing the source walk-through in §2.1):

| 📊 Structure | Role |
|---|---|
| Block Pool (block list) | Pool of all physical blocks, preallocated once at process start to avoid creating Python objects at runtime |
| Free Block Queue (free doubly linked list) | Manages free blocks; supports $O(1)$ removal from the middle ("rescuing" a block on a prefix hit) |
| Cache (hash → block ID) | Core of prefix lookup: given a block hash, is there a reusable physical block? |
| Request (request → block IDs) | Which blocks each request currently holds |

Reuse happens when the scheduler calls `get_computed_blocks()` for a new request: hash the prompt block by block, look up the Cache table; hit blocks are `touch()`ed (reference count +1, and removed from the free list so they are not evicted), then `allocate_slots()` only allocates new blocks for the miss portion.

📌 **Key point**: V1's block table is **append-only**—duplicate full blocks with the same hash can briefly coexist (the block table cannot be rewritten), and those duplicates "are cleaned up when the request is freed." That is a pragmatic V1 tradeoff for simpler scheduling; seeing duplicate blocks in the source is expected.

Eviction is the LRU from §4: when space is needed, pop the least-recently-used block from the **head** of the free list and delete its hash from the Cache table. When a request is freed, blocks are enqueued at the tail **in reverse**, so the tail block that hashed the most tokens (hardest to hit) is evicted first.

## 7. When it helps and what to watch for

✅ **High-gain scenarios for prefix caching**:

- Long system prompts / long few-shot shared by many requests
- Multi-turn chat (history keeps accumulating and getting reused)
- Parallel sampling of many outputs from the same prompt (`n > 1`)
- RAG with a fixed instruction template + varying retrieved content (put the fixed part first so it can hit)

❌ **Low or no gain**:

- Every request has a different prefix (free-form Q&A with no template)
- Shared content sits in the **middle or end** of the prompt—prefix caching only reuses the **contiguous identical stretch from the start**; shared content that is not at the beginning cannot hit

📌 **Key point**: to get the prefix-cache win, **prompt engineering should deliberately "put shared content first"**—fixed instructions, examples, and context at the front, varying user input at the end. Near-zero cost, often overlooked.

⚠️ **Note**: prefix caching **does not change model output** (reused KV is mathematically equivalent), so it is safe to leave on. In multi-tenant settings, watch isolation—vLLM provides `cache_salt` and similar mechanisms so tenants / permission domains do not accidentally hit each other's cache and leak information.

## 📝 Summary

- Prefix Cache reuses **shared-prefix KV**, skips repeated Prefill, and mainly **lowers TTFT and raises throughput**.
- Its physical basis is PagedAttention's **read-only block sharing + reference counting**, extending block sharing from concurrent requests to requests over time.
- vLLM's **Automatic Prefix Caching** detects matching prefixes with **block hashes that include the parent hash**; V1 made it near zero overhead and on by default; eviction uses **LRU + reference counting**, and reverse enqueue prefers evicting personalized tail blocks.
- SGLang's **RadixAttention** does longest-prefix match on a **Radix Tree**, with reference counting and leaf-first LRU, and fits multi-turn chat, tree sampling, and other tree-shaped reuse.
- In source, vLLM's **chained block hashes** starting from `NONE_HASH` turn prefix matching into an $O(1)$ lookup, and the four structures "block pool + free list + hash table + request table" handle reuse and LRU eviction.
- In practice, **put shared content first** so it can hit, and isolate the cache across tenants.
