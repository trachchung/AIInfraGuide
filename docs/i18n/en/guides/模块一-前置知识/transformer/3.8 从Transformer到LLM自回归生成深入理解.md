## 1. What a language model really is: predict the next word

### 1.1 Conditional probability view

Mathematically, a language model models a conditional probability distribution. Given every token that has already appeared, it outputs a distribution over the next token:

$$
P(x_t \mid x_1, x_2, \ldots, x_{t-1})
$$

The joint probability of a full sentence is the product of those conditionals:

$$
P(x_1, x_2, \ldots, x_T) = \prod_{t=1}^{T} P(x_t \mid x_1, \ldots, x_{t-1})
$$

Picture a fill-in-the-blank game. At each step you only see what is already filled in, then pick the most plausible character from all candidates. A language model does the same thing, except its "candidate table" is the whole vocab (usually 32000-128000 tokens), and it scores every candidate with a probability.

### 1.2 From Transformer output to a probability distribution

Concretely, after a token sequence runs through every Decoder Block, the last layer emits a hidden-state vector per position, shape $(N, d_{model})$. Turning that into "next-word probability" takes two more steps:

**1️⃣ LM Head**: a linear layer maps the $d_{model}$-dim hidden state to a $vocab\_size$-dim vector called **logits**:

```python
# hidden_state: (N, d_model), e.g. (N, 4096)
# lm_head.weight: (vocab_size, d_model), e.g. (32000, 4096)
logits = hidden_state @ lm_head.weight.T  # (N, vocab_size), e.g. (N, 32000)
```

**2️⃣ Softmax**: normalize logits into a probability distribution:

```python
probs = softmax(logits[-1])  # take the last position → (vocab_size,) distribution
```

We only take the last position because an autoregressive model cares about "the next word," and the output at the last token position already carries that prediction.

### 1.3 Autoregressive vs non-autoregressive

Autoregressive Generation produces tokens one by one: each step predicts the next from all existing tokens, appends it, then predicts again. Like writing: you finish one character before deciding the next.

The counterpart is **Non-Autoregressive Generation (NAR)**: generate all tokens in parallel. NAR is faster (every position can compute together), but without cross-position dependence, quality is usually worse than autoregressive. Like asking a group of people to write different parts of a sentence independently; coherence is hard.

Mainstream LLMs today (GPT series, LLaMA, Mistral, Qwen, etc.) all use autoregressive generation. NAR shows up mainly in machine translation and similar settings where quality can be relaxed a bit.

## 2. How autoregressive generation works

### 2.1 The generation loop

Autoregressive generation is a loop: each step runs a full Transformer forward pass on the current token sequence, takes the last position to predict the next token, appends it, and repeats until a stop condition.

```python
def autoregressive_generate(model, prompt_tokens, max_new_tokens, temperature=1.0):
    """Core autoregressive loop (simplified, no KV Cache)"""
    generated = list(prompt_tokens)

    for _ in range(max_new_tokens):
        # Feed the full current sequence into the model
        input_ids = torch.tensor([generated])  # (1, current_len)
        logits = model(input_ids)              # (1, current_len, vocab_size)

        # Take logits at the last position
        next_logits = logits[0, -1, :]         # (vocab_size,)

        # Temperature scaling + sampling
        probs = softmax(next_logits / temperature)
        next_token = torch.multinomial(probs, num_samples=1).item()

        # Append to the sequence
        generated.append(next_token)

        # Stop condition
        if next_token == eos_token_id:
            break

    return generated
```

That code has a serious efficiency problem: every step re-feeds the full sequence into the model. As the sequence grows, repeated compute explodes. That is exactly what KV Cache fixes; we cover it in section 6.

### 2.2 Stop conditions

Autoregressive generation needs a clear stop condition, or the model keeps going forever. Common stops:

- **EOS Token**: the model emits a special end marker `<eos>` (or `<|endoftext|>`, etc.), a natural end
- **Max length**: generated token count hits `max_new_tokens`
- **Stop string**: a specific string pattern appears (e.g. `\n\nHuman:` in chat)

## 3. Token sampling strategies

The model outputs a probability distribution. How you pick the next token from it varies. Different strategies change quality and diversity of the text.

### 3.1 Greedy Decoding

Always pick the highest-probability token:

```python
next_token = torch.argmax(probs)
```

Pros: deterministic, fast. Cons: easy to fall into repetition loops (the same phrase over and over); output is dull. Fits cases that need deterministic output (code completion, formatted output).

### 3.2 Temperature scaling

Before softmax, divide logits by a temperature $T$:

```python
probs = softmax(logits / T)
```

Temperature is a knob for how sharp the distribution is:

| Temperature | Effect | Analogy |
|--------|------|------|
| $T < 1$ (e.g. 0.3) | Sharper; high-prob tokens stand out more | Cautious author, prefers the safest word |
| $T = 1$ | Original distribution, no change | Normal play |
| $T > 1$ (e.g. 1.5) | Flatter; low-prob tokens get lifted | Wild creator, more willing to pick "surprise" words |
| $T \to 0$ | Collapses to greedy decoding | Only the most certain token |
| $T \to \infty$ | Collapses to uniform | Pure random |

### 3.3 Top-K sampling

Keep only the top $K$ tokens by probability, zero the rest, then renormalize:

```python
topk_probs, topk_indices = torch.topk(probs, k=50)
topk_probs = topk_probs / topk_probs.sum()  # renormalize
next_token = topk_indices[torch.multinomial(topk_probs, 1)]
```

Top-K's problem is that $K$ is fixed. Sometimes the mass is concentrated (only 2-3 sensible options) and $K=50$ adds too much noise; sometimes the mass is spread out (many tokens are fine) and $K=50$ is too tight.

### 3.4 Top-P sampling (Nucleus Sampling)

An adaptive scheme: sort tokens by probability descending, accumulate until the sum exceeds threshold $P$ (e.g. 0.9), then sample only inside that "nucleus":

```python
sorted_probs, sorted_indices = torch.sort(probs, descending=True)
cumsum_probs = torch.cumsum(sorted_probs, dim=0)
# Find the position where cumulative probability just exceeds p
cutoff = (cumsum_probs > p).nonzero(as_tuple=True)[0][0]
# Keep only tokens up to cutoff
nucleus_probs = sorted_probs[:cutoff + 1]
nucleus_probs = nucleus_probs / nucleus_probs.sum()
next_token = sorted_indices[torch.multinomial(nucleus_probs, 1)]
```

Top-P's strength is adaptivity: when mass is concentrated the candidate set shrinks; when spread out it grows. Like ordering food: if one dish clearly wins (concentrated mass), just order it; if several look good (spread mass), pick from a wider set.

In practice, Temperature + Top-P is the most common combo, e.g. `temperature=0.7, top_p=0.9`.

## 4. Prefill: swallow the whole prompt at once

### 4.1 What Prefill computes

When a user sends a request to an LLM, inference first enters the **Prefill** stage. Its job is to process the entire user prompt, compute and cache Key/Value for every prompt token, and emit the first generated token.

Suppose the prompt has 1000 tokens. Prefill feeds all 1000 into the Transformer at once; every token runs Self-Attention and FFN in parallel through each layer:

```
Prompt: [t_1, t_2, ..., t_1000]  (1000 tokens)
→ one forward pass
→ each layer computes Q, K, V (all for 1000 tokens)
→ cache K, V for every layer
→ take logits at position 1000 → sample the first generated token
```

### 4.2 Why Prefill is Compute Bound

Prefill's core work is large matmuls. Take Attention `Q @ K^T`:

```
Q: (1000, 128)  K^T: (128, 1000)  → result: (1000, 1000)
```

That is a real "large" matmul; GPU compute cores (Tensor Cores) can run saturated. Matmul FLOPs are high, so time spent computing far exceeds time moving data from VRAM. The bottleneck is compute, not memory bandwidth.

In Roofline terms, Prefill has high **Arithmetic Intensity**: many ops per byte moved from memory. That is exactly what GPUs are good at.

### 4.3 TTFT: the first user-facing metric

Prefill latency determines **TTFT (Time To First Token)**: time from request to the first output character.

For long prompts (e.g. upload a paper and ask for a summary), TTFT can be seconds or even tens of seconds. Ways to improve TTFT include:

- **Chunked Prefill**: split a long prompt into chunks instead of eating it whole. You can interleave other requests' Decode steps while processing the prompt, raising system throughput. Note: Chunked Prefill does not make one request's TTFT faster; it is mostly a system scheduling optimization
- **Prefix Cache / Prompt Cache**: if many requests share the same system prompt (e.g. "You are a helpful assistant"), precompute and cache that prefix's KV; later requests reuse it and skip Prefill for that segment

## 5. Decode: spit out answers token by token

### 5.1 What Decode computes

After Prefill, the model enters the **Decode** stage and generates output tokens one by one. Each step processes only 1 new token:

```
Step 1: new token Q (1, 128) × cached 1001 Keys → Attention → emit token_1001
Step 2: new token Q (1, 128) × cached 1002 Keys → Attention → emit token_1002
...
```

Each step only needs Q, K, V for the new token (one token's linear projections), then Attention between the new Q and all historical K; new K, V append to the cache.

### 5.2 Why Decode is Memory Bound

The key change in Decode: matmul collapses to **matrix-vector multiply**.

```
Prefill: Q (1000, 128) × K^T (128, 1000) = matrix × matrix → GPU saturated
Decode:  Q (1, 128)    × K^T (128, 1001) = vector × matrix → GPU idle
```

Matrix-vector multiply has little compute, but data moved from memory does not shrink in proportion: the whole K matrix `(1001, 128)` and the weight matrices still need to come from HBM to the compute cores. Compute cores spend most of their time waiting for data.

Analogy: Prefill is a fast assembly line; raw material (data) keeps arriving and workers (compute cores) stay busy. Decode is one part to machine; the worker does one touch then waits for the next part from the warehouse.

That is why Decode's bottleneck is **memory bandwidth**, not compute: we call it **Memory Bound**.

### 5.3 TPOT: how smooth it feels to the user

Per-step Decode latency determines **TPOT (Time Per Output Token)**: how fast output text "pops out" for the user.

Human reading is about 5-10 words per second (about 7-15 tokens), so TPOT under 50-100ms feels like realtime streaming. Past 200ms, lag is obvious.

### 5.4 Continuous Batching

Traditional static batching requires every request in a batch to start and finish together. Until long requests finish, GPU capacity freed by short completed requests is wasted.

**Continuous Batching** batches by iteration (one Decode step), not by whole request. After each Decode step, finished requests free resources immediately and new requests can join right away.

Like a bank queue system: the old way waits for a whole batch to finish before calling the next; continuous batching calls the next number as soon as a window frees up.

Continuous Batching was proposed in Orca and later adopted widely by vLLM, SGLang, TensorRT-LLM, and others, sharply raising GPU utilization and system throughput.

## 6. KV Cache in depth

### 6.1 Why you need KV Cache

Recall autoregressive generation: each Decode step, the new token's Q must dot with every historical token's K for Attention weights. With no cache, every step would re-run QKV projections on all history, even though those projections were already computed earlier.

Analogy: at a bank, every time you switch windows you requeue and resubmit every document. KV Cache is: file your documents once, then later windows just look up the file number.

Caching computed K and V in GPU VRAM means each Decode step only computes the new token's own K, V and appends them, cutting repeated QKV projection from $O(N)$ to $O(1)$.

### 6.2 Compute with vs without KV Cache

A simple math comparison. Let current sequence length be $n$. Per-token QKV projection cost is $3 d_{model}^2$ (three matmuls). Attention between one Query and all cached Key/Value is $O(n \cdot d_{model})$. Compare cumulative cost of generating $N$ tokens (ignore shared factor layer count $L$).

**❌ No KV Cache: each step re-feeds the whole prefix ($n$ tokens):**

Each step has $n$ Queries, each attending over $n$ Keys, so Attention cost is $n^2 \cdot d$.

| Step | QKV projection cost | Attention cost |
|------|---------------|-----------------|
| Step 1 | $1 \cdot 3d^2$ | $1^2 \cdot d$ |
| Step 2 | $2 \cdot 3d^2$ | $2^2 \cdot d$ |
| Step n | $n \cdot 3d^2$ | $n^2 \cdot d$ |
| Total ($N$ steps) | $3d^2 \cdot N(N+1)/2 = O(N^2 d^2)$ | $\sum_{n=1}^{N} n^2 d = O(N^3 d)$ |

**⭕ With KV Cache: each step only computes QKV for 1 new token:**

Each step has 1 Query attending over $n$ cached K/V.

| Step | QKV projection cost | Attention cost |
|------|---------------|-----------------|
| Step n | $1 \cdot 3d^2$ | $n \cdot d$ (still dots with all cached K) |
| Total ($N$ steps) | $N \cdot 3d^2 = O(Nd^2)$ | $O(N^2 d)$ |

KV Cache drops total QKV projection from $O(N^2 d^2)$ to $O(N d^2)$, an $N\times$ save; total Attention from $O(N^3 d)$ to $O(N^2 d)$, also $N\times$. At long sequences that is an order-of-magnitude gap.

### 6.3 KV Cache data structure

KV Cache is a set of tensors storing Key and Value for every processed token at every layer:

```python
# For each layer layer_i, keep two tensors:
kv_cache = {
    layer_0: {
        'key':   tensor of shape (batch_size, num_kv_heads, current_seq_len, head_dim),
        'value': tensor of shape (batch_size, num_kv_heads, current_seq_len, head_dim),
    },
    layer_1: { ... },
    ...
    layer_31: { ... },
}
```

Each Decode step appends the new token's K and V on the `current_seq_len` dim:

```python
# Compute new token K, V
new_k = linear_k(new_hidden_state)  # (batch, num_kv_heads, 1, head_dim)
new_v = linear_v(new_hidden_state)  # (batch, num_kv_heads, 1, head_dim)

# Append to cache
kv_cache[layer_i]['key'] = torch.cat([kv_cache[layer_i]['key'], new_k], dim=2)
kv_cache[layer_i]['value'] = torch.cat([kv_cache[layer_i]['value'], new_v], dim=2)

# Attention uses the full cache
attn_output = attention(new_q, kv_cache[layer_i]['key'], kv_cache[layer_i]['value'])
```

### 6.4 KV Cache VRAM formula

KV Cache VRAM has a general formula:

$$
\text{KV Cache VRAM} = 2 \times L \times n_{kv} \times d_h \times N \times B \times b_e
$$

where:
- $2$: one copy each for K and V
- $L$: layer count (num_layers)
- $n_{kv}$: number of KV heads (equals num_heads for MHA, num_kv_groups for GQA)
- $d_h$: head dim (head_dim)
- $N$: sequence length (seq_len)
- $B$: batch size
- $b_e$: bytes per element; FP16 is 2, FP8 is 1

Typical configs:

| Model | Layers | KV heads | $d_h$ | Per-token KV Cache (FP16) | 4K seq | 128K seq |
|------|------|--------|----------|------------------------|------------|--------------|
| LLaMA-2-7B (MHA) | 32 | 32 | 128 | 512 KB | 2 GB | 64 GB |
| LLaMA-2-7B (GQA-8) | 32 | 8 | 128 | 128 KB | 0.5 GB | 16 GB |
| LLaMA-3-8B (GQA-8) | 32 | 8 | 128 | 128 KB | 0.5 GB | 16 GB |
| LLaMA-2-70B (GQA-8) | 80 | 8 | 128 | 320 KB | 1.25 GB | 40 GB |

From the table:

1. **GQA cuts KV Cache a lot**: 32 KV heads down to 8 is a 4× shrink
2. **Long context eats VRAM**: at 128K, one request's KV Cache can fill a whole GPU
3. **Batch multiplier**: serve 16 requests at once and multiply the numbers by 16

### 6.5 Memory fragmentation

KV Cache has a nasty engineering problem: **fragmentation from dynamic growth**.

Different requests have different lengths, so KV Cache sizes differ. As requests arrive and finish, VRAM fills with holes: total free memory is enough, but no contiguous region fits a new request's KV Cache. Like a parking lot with many single spots but none adjacent for a car that needs two consecutive spaces.

The old approach preallocates max-seq-len KV Cache per request, which wastes hugely: most requests never use the max. That is the core problem PagedAttention solves.

## 7. A tour of KV Cache optimizations

### 7.1 PagedAttention: borrow OS virtual memory

PagedAttention is the core idea in the vLLM inference engine, taken straight from OS **virtual memory paging**.

The OS problem and KV Cache management look almost the same: processes need different memory sizes; create/destroy leaves physical memory fragmented. The OS fix: stop giving each process contiguous physical memory; split physical memory into fixed-size pages and map virtual addresses to non-contiguous physical pages via a page table.

PagedAttention does the same thing:

1. **Paging**: split GPU VRAM into fixed-size Blocks (e.g. each Block holds KV for 16 tokens)
2. **Allocate on demand**: start with a few Blocks, append more as generation grows
3. **No contiguity required**: one request's KV Cache can live in non-contiguous Blocks; a Block Table (like a page table) records the mapping
4. **Reclaim**: free Blocks as soon as a request finishes, for other requests

```
Traditional (preallocate contiguous VRAM):
Request A: [████████░░░░░░░░]  ← preallocate max_len, lots of waste
Request B: [██████████░░░░░░]

PagedAttention (paged management):
Block pool: [A1][B1][A2][B2][A3][free][B3][free][free]...
Block Table A: [1, 3, 5]   ← request A's KV in Blocks 1, 3, 5
Block Table B: [2, 4, 7]   ← request B's KV in Blocks 2, 4, 7
```

PagedAttention's impact is large: experiments show KV Cache utilization can rise from about 20-40% to near 100%, supporting 2-4× more concurrent requests on the same VRAM.

### 7.2 Prefix Cache / Prompt Cache

In many workloads, requests share a prefix, e.g. the same system prompt ("You are a helpful AI assistant, please..."). Recomputing that prefix KV for every request is waste.

Prefix Cache: compute shared-prefix KV once and cache it; later requests with the same prefix reuse it and only Prefill their own suffixes.

SGLang's **RadixAttention** goes further: a Radix Tree manages prefix-sharing across requests for finer reuse.

### 7.3 KV Cache quantization

Since KV Cache is a VRAM hog, store it at lower precision:

| Precision | Bytes per element | Compression vs FP16 | Quality loss |
|------|-------------|---------------------|---------|
| FP16 | 2 | 1x (baseline) | None |
| FP8 (E4M3) | 1 | 2x | Tiny |
| INT8 | 1 | 2x | Small |
| INT4 | 0.5 | 4x | Medium |

The challenge: Attention is sensitive to Key precision (Q·K products set attention weight allocation) and more tolerant of Value precision. Some schemes quantize K and V differently.

### 7.4 GQA / MQA: fewer KV heads

Shrink KV Cache from the architecture side:

- **MHA (Multi-Head Attention)**: each attention head has its own K and V; KV heads = total heads
- **MQA (Multi-Query Attention)**: all attention heads share one K/V set; KV heads = 1
- **GQA (Grouped-Query Attention)**: every $G$ heads share one K/V set; KV heads = total heads / $G$

For a 32-head model: MHA has 32 KV groups, GQA-8 has 4 (8× fewer), MQA has 1 (32× fewer). KV Cache size scales with KV head count, so GQA/MQA save a lot of inference VRAM.

### 7.5 Sliding Window Attention

Mistral introduced **sliding window attention**: each token only attends to the most recent $W$ tokens (e.g. $W=4096$), not full history. KV Cache only needs the latest $W$ tokens' K, V; older ones can be dropped.

KV Cache goes from $O(N)$ to $O(W)$, a huge save on ultra-long sequences. The cost: the model cannot directly access info outside the window (it relies on multi-layer stacking to pass information indirectly).

### 7.6 Token Eviction / Token Dropping

A more aggressive strategy: when KV Cache hits a capacity limit, actively drop KV for "unimportant" tokens.

Ways to score importance:
- **Attention scores**: tokens with low cumulative Attention weight may matter less (H2O: Heavy-Hitter Oracle)
- **Position**: keep leading tokens (often the system prompt; "attention sink") and recent tokens; drop the middle
- **Semantics**: keep key entities, numbers, etc.

## 8. System-level inference optimizations

### 8.1 Prefill/Decode disaggregation

As above, Prefill is Compute Bound and Decode is Memory Bound: their hardware needs differ. Running both on the same GPU pool means the hardware is a compromise, optimal for neither.

**Prefill/Decode disaggregation** (DistServe, Splitwise, etc.): put Prefill and Decode on different GPU pools:

- **Prefill pool**: high-compute GPUs, dedicated to prompt compute
- **Decode pool**: high-bandwidth GPUs (or more cheaper GPUs), dedicated to token-by-token generation

After Prefill, ship KV Cache to the Decode pool to continue. Each pool can be tuned for its job; overall efficiency rises.

### 8.2 Speculative Decoding

The fundamental bottleneck of autoregressive generation is serial: each step waits for the previous. Speculative decoding tries to break that:

1. A **small model** (Draft Model, e.g. a 1B distilled sibling of a 7B) quickly proposes $K$ candidate tokens (e.g. $K=5$)
2. Feed those $K$ candidates into the **large model** (Target Model) for parallel verification
3. The large model checks whether the small model's prediction matches at each position:
   - Matching tokens are accepted
   - At the first mismatch the large model resamples; later candidates are discarded

If the draft is accurate enough (say 70-80% of tokens accepted), one verification confirms multiple tokens, equivalent to emitting multiple tokens per step, lifting Decode throughput several times.

The hard constraint: speculative decoding must keep results distributionally identical to the large model alone; quality must not drop.

### 8.3 Tensor Parallelism in inference

Inference tensor parallelism uses the same splits as training (along Attention heads and FFN matrices), but for a different goal:

- Training: split so a large model fits across cards (VRAM limit)
- Inference: split to cut per-step latency (multi-GPU parallel compute, lower TPOT)

Tensor parallelism also adds communication (AllReduce every Decode step), so it is usually limited to GPUs in one node (NVLink). Across nodes, pipeline parallelism fits better.

## 9. Inference performance metrics

Inference performance needs a full metric set; different roles care about different ones:

### 9.1 Latency metrics (user view)

| Metric | Full name | Meaning | Typical target |
|------|------|------|---------|
| TTFT | Time To First Token | Request sent → first output token | < 500ms |
| TPOT | Time Per Output Token | Gap between output tokens | < 100ms |
| E2E Latency | End-to-End Latency | Request sent → full response | Depends on generation length |

Relation: `E2E Latency = TTFT + TPOT * (output_length - 1)`

### 9.2 Throughput metrics (system view)

| Metric | Meaning | Optimization direction |
|------|------|---------|
| Tokens/s | Total tokens processed per second | Larger batch_size, higher GPU utilization |
| Requests/s | Requests completed per second | Continuous Batching, less queue wait |
| GPU Utilization | Compute-core utilization | Larger batch_size (often low in Decode) |

### 9.3 Efficiency metrics (cost view)

| Metric | Meaning | How computed |
|------|------|---------|
| $/1K tokens | Inference cost per thousand tokens | GPU cost / total tokens processed |
| Tokens/$/hour | Tokens processed per dollar per hour | Throughput / GPU-hour cost |

Latency and throughput often trade off: larger batch_size raises throughput (more requests in parallel) but increases per-request TPOT (each step touches more tokens' KV Cache). Tuning an inference system is maximizing throughput under a latency SLA.

## 📝 Summary

Starting from the math of language models, this article walked the full autoregressive generation path:

1. **Language model essence**: model $P(x_t \mid x_1,\ldots,x_{t-1})$
2. **Autoregressive loop**: predict + sample + append until stop
3. **Sampling**: Temperature controls randomness; Top-K/Top-P control the candidate set
4. **Prefill**: process the prompt in parallel, Compute Bound, sets TTFT
5. **Decode**: generate token by token, Memory Bound, sets TPOT
6. **KV Cache**: avoid recomputing K/V; trade space for time
7. **KV Cache optimizations**: PagedAttention (paging), Prefix Cache (prefix reuse), quantization (lower precision), GQA (fewer heads)
8. **System optimizations**: Continuous Batching, Prefill/Decode disaggregation, Speculative Decoding

For AI Infra engineers, these inference mechanics are the base for designing and optimizing serving systems. Every optimization comes from digging into one link: Prefill's Compute Bound led to Chunked Prefill; Decode's Memory Bound led to Speculative Decoding; KV Cache pressure led to PagedAttention and quantization.
