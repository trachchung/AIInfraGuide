## 1. Bắt đầu từ một đoạn ví dụ

Đọc engine thì trước hết xem nó được gọi thế nào. Quick Start trong README và `example.py` ở thư mục gốc chỉ dùng ba API công khai: `LLM`, `SamplingParams` và `generate`. Dưới đây là cách dùng tối giản viết theo kiểu `example.py`:

```python
import os
from transformers import AutoTokenizer
from nanovllm import LLM, SamplingParams

path = os.path.expanduser("~/huggingface/Qwen3-0.6B/")   # Thư mục mô hình local

# 1) Khởi tạo engine: đường dẫn local + các công tắc toàn cục
llm = LLM(path, enforce_eager=True, tensor_parallel_size=1)

# 2) Định nghĩa chiến lược sampling
sampling_params = SamplingParams(temperature=0.6, max_tokens=256)

# 3) Mô hình chat: bọc chat template rồi mới đưa vào engine
tokenizer = AutoTokenizer.from_pretrained(path)
questions = ["Giới thiệu PagedAttention trong một câu", "Các số nguyên tố dưới 100"]
prompts = [
    tokenizer.apply_chat_template([{"role": "user", "content": q}],
                                  tokenize=False, add_generation_prompt=True)
    for q in questions
]

# 4) Sinh theo batch: mỗi phần tử là {"text": ..., "token_ids": ...}
outputs = llm.generate(prompts, sampling_params)
print(outputs[0]["text"])
```

Trong đoạn mã có ba chi tiết:

- Khi khởi tạo `LLM`, tham số đầu là **đường dẫn thư mục local**, không phải tên repo HuggingFace. `Config` assert `os.path.isdir(model)`; trọng số được `safetensors` nạp từ đĩa local; nano-vllm không lo tải về.
- `generate` trả về **danh sách dict** (có `"text"` và `"token_ids"`); vLLM trả về object `RequestOutput`. README gọi đây là «minor differences» so với API vLLM.
- Chat template do phía gọi xử lý. `example.py` dùng `apply_chat_template(..., tokenize=False, add_generation_prompt=True)` để bọc câu hỏi thành chuỗi dạng hội thoại trước; bên trong engine chỉ `encode`, không tự bọc template.

⚠️ **Lưu ý**: Quick Start trong README đưa thẳng văn bản trần kiểu `"Hello, Nano-vLLM."` vào `generate`—dùng để demo API được, nhưng Qwen3 là mô hình hội thoại; không bọc template thì chất lượng đầu ra tụt rõ. Thực tế hãy theo cách viết của `example.py`.

Tiếp theo lần lượt xem các trường của `Config` và `SamplingParams`, việc `LLM` làm khi khởi tạo, và vòng lặp bên trong `generate`.

## 2. Config: cấu hình toàn cục

`Config` trong `config.py` là một `@dataclass(slots=True)`, gom các ràng buộc toàn cục engine cần vào một chỗ. Các trường và mặc định:

```python
@dataclass(slots=True)
class Config:
    model: str                              # Thư mục mô hình local (bắt buộc)
    max_num_batched_tokens: int = 16384     # Tổng token tối đa một bước (Token Budget)
    max_num_seqs: int = 512                 # Số sequence đồng thời tối đa một bước
    max_model_len: int = 4096               # Độ dài context tối đa hỗ trợ
    gpu_memory_utilization: float = 0.9     # Tỷ lệ VRAM được phép chiếm
    tensor_parallel_size: int = 1           # Số GPU tensor parallelism
    enforce_eager: bool = False             # True thì tắt CUDA Graph
    hf_config: AutoConfig | None = None     # Cấu hình HF nạp trong __post_init__
    eos: int = -1                           # EOS token id (sau init do tokenizer điền)
    kvcache_block_size: int = 256           # Số token mỗi khối KV
    num_kvcache_blocks: int = -1            # Tổng số khối KV (runtime suy từ VRAM)
```

Sau khi khởi tạo, `__post_init__` chạy ba assert, nạp cấu hình HF, và cắt độ dài context về trần mô hình hỗ trợ:

```python
def __post_init__(self):
    assert os.path.isdir(self.model)                 # Phải là thư mục local tồn tại
    assert self.kvcache_block_size % 256 == 0        # Kích thước khối phải là bội của 256
    assert 1 <= self.tensor_parallel_size <= 8       # Mức TP trong khoảng 1~8
    self.hf_config = AutoConfig.from_pretrained(self.model)
    self.max_model_len = min(self.max_model_len,
                             self.hf_config.max_position_embeddings)
```

Vài trường đáng chú ý:

- 🔑 **`kvcache_block_size = 256`**: mỗi khối KV chứa bao nhiêu token. Khối càng lớn, Block Table càng ngắn, chi phí quản lý càng nhỏ, nhưng mảnh nội bộ khi khối cuối chưa đầy cũng càng lớn. Assert `% 256 == 0` đến từ yêu cầu toán tử phía dưới: tài liệu `flash_attn_with_kvcache` của flash-attn ghi rõ, khi truyền `block_table` (KV phân trang) thì `page_block_size` phải là bội của 256. Đường decode và đường prefill khi trúng prefix của nano-vllm đều đọc KV phân trang qua `block_table`, nên kích thước khối chỉ lấy được các giá trị kiểu 256, 512. 256 là giá trị nhỏ nhất được phép, không phải điểm cân bằng chọn giữa mảnh và chi phí.

> ⏰ **Thông tin theo thời điểm**: `256` là mặc định hiện tại của nano-vllm. vLLM dùng kernel PagedAttention riêng và mặc định phổ biến `block_size=16`; đừng lẫn hai mặc định.

- 🔑 **`max_num_batched_tokens` và `max_num_seqs`**: cái trước giới hạn một bước tính tối đa bao nhiêu token (chủ yếu ràng prefill); cái sau giới hạn một bước tối đa bao nhiêu sequence (chủ yếu ràng decode). Hai cái cùng tạo **Token Budget** của scheduler; 3.5 sẽ nói kỹ.
- 🔑 **`gpu_memory_utilization = 0.9`**: engine không dành sẵn KV theo độ dài tối đa cho mọi request; nó nạp trọng số trước, chạy một lần prefill quy mô tối đa để đo đỉnh activation, rồi cắt toàn bộ hạn mức còn lại thành khối KV. Vì thế `num_kvcache_blocks` khởi đầu là `-1`, chỉ tính lúc runtime; công thức xem 3.6.
- **`tensor_parallel_size ≤ 8`**: trần 8 GPU một máy. Mức TP thực dùng còn bị mô hình ràng: implementation Qwen3 yêu cầu số đầu attention và số đầu KV đều chia hết cho mức TP; xem 3.3.

## 3. SamplingParams: siêu tham số sampling

So với vài chục tham số sampling của vLLM, `SamplingParams` của nano-vllm chỉ có ba trường:

```python
@dataclass(slots=True)
class SamplingParams:
    temperature: float = 1.0
    max_tokens: int = 64
    ignore_eos: bool = False

    def __post_init__(self):
        assert self.temperature > 1e-10, "greedy sampling is not permitted"
```

- **`temperature`**: nhiệt độ; điều khiển độ ngẫu nhiên khi sample.
- **`max_tokens`**: sinh tối đa bao nhiêu token; mặc định `64` (ví dụ set tường minh thành `256`). Nó vừa là điều kiện dừng, vừa dùng để cố định lượng sinh khi benchmark.
- **`ignore_eos`**: có bỏ qua EOS để tiếp tục sinh không. `bench.py` set `True` để mọi sequence đều sinh đủ `max_tokens`, số liệu thông lượng mới so sánh được.

📌 **Điểm then chốt**: `__post_init__` assert nhiệt độ phải lớn hơn `1e-10`, nghĩa là **nano-vllm không hỗ trợ greedy sampling** (temperature=0). `Sampler` của nó chỉ có một đường sampling ngẫu nhiên: chia logits cho nhiệt độ rồi softmax, sau đó argmax với nhiễu mũ (xem 3.3). Nhiệt độ 0 sẽ làm phép chia lỗi; tác giả không viết nhánh argmax riêng cho trường hợp đó mà chặn ngay ở cửa vào. Muốn đầu ra gần xác định, hãy set nhiệt độ thành một số dương rất nhỏ.

## 4. LLM và LLMEngine: khi khởi tạo làm gì

`llm.py` chỉ 5 dòng; `LLM` kế thừa trực tiếp `LLMEngine`, thân lớp là `pass`, các phương thức như `generate` đều lấy từ lớp cha. Mọi việc khởi tạo nằm trong `LLMEngine.__init__`, chia bốn bước:

```python
class LLMEngine:
    def __init__(self, model, **kwargs):
        # 1) Lọc các trường Config biết từ kwargs, dựng cấu hình toàn cục
        config_fields = {f.name for f in fields(Config)}
        config = Config(model, **{k: v for k, v in kwargs.items()
                                   if k in config_fields})
        # Đồng bộ kích thước khối sang Sequence (nó ghi block_size bằng biến lớp)
        Sequence.block_size = config.kvcache_block_size

        # 2) Tensor parallelism: dùng spawn khởi động worker con cho rank>0
        ctx = mp.get_context("spawn")
        self.ps, self.events = [], []
        for rank in range(1, config.tensor_parallel_size):
            event = ctx.Event()
            p = ctx.Process(target=ModelRunner, args=(config, rank, event))
            p.start()
            self.ps.append(p); self.events.append(event)
        # ModelRunner của rank 0 chạy ở tiến trình chính
        self.model_runner = ModelRunner(config, 0, self.events)

        # 3) Tokenizer chỉ giữ ở tiến trình chính; ghi EOS ngược vào config
        self.tokenizer = AutoTokenizer.from_pretrained(config.model, use_fast=True)
        config.eos = self.tokenizer.eos_token_id

        # 4) Scheduler + dọn khi thoát
        self.scheduler = Scheduler(config)
        atexit.register(self.exit)
```

Vài chi tiết kỹ thuật ở đây:

- 🔑 **Vì sao dùng `spawn` chứ không dùng `fork` mặc định trên Linux**: CUDA runtime không hỗ trợ khởi tạo lại trong tiến trình con do `fork` tạo. Cha đã init CUDA rồi thì con `fork` ra rồi dùng GPU sẽ lỗi. `spawn` khởi một tiến trình interpreter mới hoàn toàn; mỗi rank tự init GPU của mình.
- 🔑 **Cha–con giao tiếp bằng shared memory + `Event`**: `ModelRunner` của `rank>0` ở cuối `__init__` của tiến trình con vào vòng chờ nhiệm vụ. Tiến trình chính pickle tên phương thức và tham số rồi ghi vào shared memory, rồi `set` `Event` của từng worker để nó đọc. Chi tiết xem 3.6.
- **Tokenizer chỉ ở tiến trình chính**: encode và decode là việc CPU; TP worker chỉ cần token id, không cần mỗi tiến trình nạp một tokenizer.
- **Dọn bằng `atexit`**: khi thoát, cùng đường RPC gửi `"exit"` cho tiến trình con rồi `join` thu hồi, tránh process sót.

💡 **Gợi ý**: dòng `Sequence.block_size = config.kvcache_block_size` dễ bị bỏ qua. `Sequence` dùng **biến lớp** ghi kích thước khối; mọi sequence chia sẻ cùng một giá trị; các thuộc tính như `num_blocks`, `last_block_num_tokens` đều dựa vào nó.

## 5. Vòng lặp chính: add_request → step → postprocess

Khung xương của `generate` (đã bỏ thanh tiến trình tqdm và thống kê thông lượng):

```python
def generate(self, prompts, sampling_params, use_tqdm=True):
    # Một SamplingParams được nhân bản cho mọi prompt; cũng có thể truyền list cùng độ dài
    if not isinstance(sampling_params, list):
        sampling_params = [sampling_params] * len(prompts)
    for prompt, sp in zip(prompts, sampling_params):
        self.add_request(prompt, sp)

    outputs = {}
    while not self.is_finished():
        finished, num_tokens = self.step()   # Chạy một bước; lấy các sequence xong ở bước này
        for seq_id, token_ids in finished:
            outputs[seq_id] = token_ids

    # Thứ tự hoàn thành khác thứ tự submit; sắp theo seq_id để khôi phục
    outputs = [outputs[i] for i in sorted(outputs)]
    return [{"text": self.tokenizer.decode(ids), "token_ids": ids}
            for ids in outputs]
```

`seq_id` do bộ đếm cấp lớp của `Sequence` tăng dần cấp, nên sắp theo `seq_id` cũng chính là sắp theo thứ tự submit. Prompt ngắn thường kết thúc trước; không có bước sắp này thì thứ tự trả về lệch so với đầu vào.

Hai phương thức then chốt:

**`add_request`**: biến một prompt thành một `Sequence` đưa vào scheduler. Prompt có thể là chuỗi (bên trong `encode` trước) hoặc danh sách token id sẵn:

```python
def add_request(self, prompt, sampling_params):
    if isinstance(prompt, str):
        prompt = self.tokenizer.encode(prompt)
    self.scheduler.add(Sequence(prompt, sampling_params))
```

**`step`**: một vòng «schedule → forward → ghi lại» đầy đủ:

```python
def step(self):
    seqs, is_prefill = self.scheduler.schedule()                  # Chọn batch
    # Phải thống kê trước postprocess: postprocess sẽ xóa num_scheduled_tokens
    num_tokens = sum(seq.num_scheduled_tokens for seq in seqs) if is_prefill else -len(seqs)
    token_ids = self.model_runner.call("run", seqs, is_prefill)  # Chạy mô hình + sample
    self.scheduler.postprocess(seqs, token_ids, is_prefill)      # Ghi lại, quyết định kết thúc
    outputs = [(seq.seq_id, seq.completion_token_ids)
               for seq in seqs if seq.is_finished]
    return outputs, num_tokens
```

📌 **Điểm then chốt**: `num_tokens` dùng **dấu dương/âm** để phân giai đoạn. Prefill trả số dương—tổng token thực tính ở bước này (bật chunked prefill thì có thể chỉ là một phần prompt); decode trả kích thước batch âm `-len(seqs)`. `generate` dựa vào dấu để tính riêng thông lượng Prefill và Decode (tok/s) hiện trên thanh tiến trình. Dòng này không được chuyển xuống sau `postprocess`, nếu không `num_scheduled_tokens` đã bị xóa và thông lượng prefill sẽ luôn hiện 0.

Phân công trong vòng lặp: **`model_runner.call("run", ...)` lo cách tính; `scheduler` lo tính ai và tính xong làm gì**. `call` khi TP=1 chỉ là gọi phương thức thường; khi TP>1 còn broadcast cùng một lời gọi sang các rank khác. Ba mục sau lần lượt mở lớp thực thi (3.3), quản lý KV (3.4) và lớp scheduling (3.5); 3.6 quay lại `ModelRunner` để nối chúng lại.

## 📝 Tóm tắt

- API công khai mà README và `example.py` dùng chỉ có `LLM`, `SamplingParams`, `generate`, trả về danh sách dict có `"text"` và `"token_ids"`; chat template do phía gọi tự bọc.
- `Config` là `@dataclass(slots=True)`, quản lý tập trung tỷ lệ VRAM, Token Budget, mức TP, kích thước khối KV. `kvcache_block_size % 256 == 0` đến từ yêu cầu KV phân trang của flash-attn.
- `SamplingParams` chỉ có ba trường và assert nhiệt độ > `1e-10`; không hỗ trợ greedy sampling.
- `LLM` là lớp con rỗng của `LLMEngine`. `LLMEngine.__init__` dùng `spawn` khởi động TP worker, chỉ giữ tokenizer ở tiến trình chính, đăng ký dọn bằng `atexit`.
- Vòng lặp chính là `generate → add_request → step → postprocess`. `step` thống kê `num_tokens` trước `postprocess` và dùng dấu để phân prefill / decode; cuối cùng `generate` sắp theo `seq_id` để khôi phục thứ tự submit.

## 🎯 Checklist tự kiểm

- Viết được đoạn suy luận tối giản với `LLM` và `SamplingParams` có chat template, và lấy được `outputs[0]["text"]`
- Nói được `max_num_batched_tokens`, `max_num_seqs`, `gpu_memory_utilization`, `kvcache_block_size` của `Config` mỗi cái ràng gì
- Giải thích vì sao `kvcache_block_size` phải là bội của 256
- Giải thích vì sao nano-vllm không hỗ trợ greedy sampling
- Nói rõ vì sao `LLMEngine` dùng `spawn` chứ không `fork` để khởi tiến trình tensor parallelism
- Thuật lại thứ tự thực thi của `step()`, và vì sao `num_tokens` phải tính trước `postprocess`
- Giải thích vì sao `generate` phải sắp theo `seq_id` rồi mới trả về
