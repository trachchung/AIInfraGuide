## 1. Vị trí của ModelRunner

Các mục trước lần lượt nói tính toán tử nào (3.3), KV để đâu (3.4), tính ai (3.5). `ModelRunner` (`engine/model_runner.py`, 257 dòng) nối chúng thành một lần thực thi GPU thật: nhận các chuỗi scheduler đã chọn, dựng tensor mà `forward` cần, đặt context toàn cục, gọi `Qwen3`, rồi đưa logits cho sampler.

Khung nét đứt là một lần `ModelRunner.run`. Trong khung, năm bước chạy từ trái sang phải; hai bước xanh gọi chính mô hình:

<img src="/AIInfraGuide/images/inference-engine/nano-vllm-model-runner-pipeline.svg" alt="Năm bước của ModelRunner.run: sau khi Scheduler chọn seqs và is_prefill, run lần lượt ① tensor hóa và set_context (input_ids, positions, slot_mapping, ...), ② run_model (eager hoặc replay CUDA Graph), ③ compute_logits, ④ Sampler sample token tiếp (chỉ rank 0), ⑤ reset_context" style="max-width: 100%; display: block; margin: 0 auto;" />

Bản thân `run` chỉ vài dòng:

```python
def run(self, seqs, is_prefill):
    input_ids, positions = self.prepare_prefill(seqs) if is_prefill else self.prepare_decode(seqs)
    temperatures = self.prepare_sample(seqs) if self.rank == 0 else None
    logits = self.run_model(input_ids, positions, is_prefill)   # eager hoặc replay CUDA Graph
    token_ids = self.sampler(logits, temperatures).tolist() if self.rank == 0 else None
    reset_context()
    return token_ids
```

`ModelRunner.__init__` lúc engine khởi động làm xong phần chuẩn bị theo thứ tự cố định; các mục sau sẽ mở từng phần:

1. Khởi tạo process group bằng NCCL, gắn GPU của rank này, đặt dtype mặc định bằng dtype của mô hình (Qwen3-0.6B là bf16).
2. Dựng `Qwen3ForCausalLM` và nạp trọng số từ safetensors.
3. `warmup_model`: chạy một lần prefill kích thước tối đa, đo đỉnh kích hoạt (mục 4).
4. `allocate_kv_cache`: cắt bộ nhớ GPU còn lại thành các khối KV (mục 4).
5. Khi `enforce_eager=False` thì `capture_cudagraph`, capture trước CUDA Graph cho decode (mục 5).
6. Khi TP>1 thì tạo shared memory; rank>0 vào `loop` chờ lệnh (mục 6).

## 2. Biến chuỗi thành tensor: prepare_prefill / prepare_decode

`forward` của mô hình nhận tensor; scheduler đưa một batch đối tượng `Sequence`. `ModelRunner` chuyển đổi bằng hai hàm prepare theo giai đoạn, vì hai giai đoạn cần hình dạng tensor khác nhau.

**Prefill: ghép các chuỗi độ dài khác nhau nối đuôi nhau**

```python
def prepare_prefill(self, seqs):
    input_ids, positions, slot_mapping = [], [], []
    cu_seqlens_q, cu_seqlens_k = [0], [0]
    max_seqlen_q = max_seqlen_k = 0
    block_tables = None
    for seq in seqs:
        start = seq.num_cached_tokens               # số token đã nằm trong Cache
        end = start + seq.num_scheduled_tokens      # vòng này tính đến đâu
        input_ids.extend(seq[start:end])            # Q chỉ chứa token tính vòng này
        positions.extend(range(start, end))         # vị trí nối tiếp từ start
        cu_seqlens_q.append(cu_seqlens_q[-1] + end - start)
        cu_seqlens_k.append(cu_seqlens_k[-1] + end) # K phủ mọi token từ đầu đến end
        max_seqlen_q = max(max_seqlen_q, end - start)
        max_seqlen_k = max(max_seqlen_k, end)
        if not seq.block_table:                     # chuỗi giả của warmup không có khối; không ghi Cache
            continue
        # ánh xạ [start, end) thành slot vật lý (mã nguồn extend theo đoạn khối; ở đây mở từng token)
        for i in range(start, end):
            block_id = seq.block_table[i // self.block_size]
            slot_mapping.append(block_id * self.block_size + i % self.block_size)
    if cu_seqlens_k[-1] > cu_seqlens_q[-1]:         # có KV lịch sử: trúng prefix hoặc tiếp tục chunked
        block_tables = self.prepare_block_tables(seqs)
    # ...đổi thành tensor pin_memory, copy non_blocking sang GPU, rồi set_context(True, ...)
```

- 🔑 **`cu_seqlens` (cumulative sequence lengths)**: sau khi nhiều chuỗi độ dài khác nhau nối đuôi nhau, một mảng độ dài tích lũy đánh dấu biên mỗi chuỗi. Đó là định dạng `flash_attn_varlen_func` yêu cầu (xem 3.3). Phía Q chỉ có token tính vòng này; phía K tính từ đầu chuỗi.
- 🔑 **Khi nào mang `block_tables`**: không có lịch sử thì Q và K cùng dài, kernel dùng thẳng k/v vừa tính vòng này. Chỉ cần một chuỗi có K dài hơn Q nghĩa là nửa trước KV của nó đã nằm trong Cache; lúc đó mới chuẩn bị `block_tables`, Attention chuyển sang đọc đủ K/V từ Cache (mục 7.2 của 3.3).
- **`slot_mapping`**: vị trí vật lý của mỗi token trong KV Cache, bằng `chỉ_số_khối_vật_lý × block_size + lệch_trong_khối`. Triton `store_kvcache` ở 3.3 ghi K/V vào Cache theo map này.

Hình dưới dùng block_size = 4 minh họa một chuỗi 10 token trúng 1 khối prefix cache (xám = token đã trong Cache; cam = token tính vòng này):

<img src="/AIInfraGuide/images/inference-engine/nano-vllm-slot-mapping.svg" alt="block_size=4, block_table=[7,2,5] cho chuỗi 10 token: khối 0 trúng prefix cache, num_cached_tokens=4; vòng này tính t4 đến t9 (6 token), slot_mapping là 8–11 cộng 20, 21; cu_seqlens_q=[0,6], cu_seqlens_k=[0,10]" style="max-width: 100%; display: block; margin: 0 auto;" />

**Decode: mỗi chuỗi chỉ một token**

```python
def prepare_decode(self, seqs):
    input_ids, positions, slot_mapping, context_lens = [], [], [], []
    for seq in seqs:
        input_ids.append(seq.last_token)          # chỉ đưa token vừa sample ở bước trước
        positions.append(len(seq) - 1)
        context_lens.append(len(seq))             # tổng độ dài gồm cả token mới này
        # token mới là token thứ last_block_num_tokens trong khối cuối
        slot_mapping.append(seq.block_table[-1] * self.block_size + seq.last_block_num_tokens - 1)
    block_tables = self.prepare_block_tables(seqs)  # pad block_table của mỗi chuỗi bên phải bằng -1 thành ma trận
    # ...đổi thành tensor GPU, set_context(False, slot_mapping=..., context_lens=..., block_tables=...)
```

- **Đọc `last_token` chứ không phải `token_ids[-1]`**: khi TP>1, chuỗi decode mà worker nhận chỉ có `last_token`, không có `token_ids` (mục 3.1 của 3.4).
- **Vị trí của slot**: scheduler trong `may_append` đã cấp khối mới cho token vượt biên, nên token mới luôn nằm trong `block_table[-1]`.
- 🔑 **`context_lens`**: bảo `flash_attn_with_kvcache` mỗi chuỗi đọc bao nhiêu K/V lịch sử. Nó tính cả token mới, vì Attention chạy `store_kvcache` trước để ghi K/V của token mới vào Cache, rồi mới tính attention.

⚠️ **Lưu ý**: `-1` pad bên phải của `block_tables` chỉ để căn ma trận. Kernel chỉ đọc các khối hợp lệ phía trước theo `context_lens`, không đụng phần pad. Nó khác với `slot == -1` mà `store_kvcache` bỏ qua; những slot đó đến từ việc pad batch khi replay CUDA Graph (mục 5).

## 3. Context toàn cục: "tham số ẩn" của các toán tử

Các tensor như `cu_seqlens`, `slot_mapping`, `block_tables`, `is_prefill` đều được Attention, LMHead và các toán tử khác dùng. Nếu truyền như tham số hàm từng lớp, `Qwen3ForCausalLM`, mỗi `DecoderLayer`, mỗi `Attention.forward` sẽ thêm bảy tám tham số. nano-vllm đặt chúng vào một **Context toàn cục** (`utils/context.py`); toán tử lấy bằng `get_context()`:

```python
@dataclass(slots=True)
class Context:
    is_prefill: bool = False
    cu_seqlens_q: torch.Tensor | None = None
    cu_seqlens_k: torch.Tensor | None = None
    max_seqlen_q: int = 0
    max_seqlen_k: int = 0
    slot_mapping: torch.Tensor | None = None
    context_lens: torch.Tensor | None = None
    block_tables: torch.Tensor | None = None

_CONTEXT = Context()

def set_context(is_prefill, cu_seqlens_q=None, ...):   # gọi ở cuối prepare_*
    global _CONTEXT
    _CONTEXT = Context(is_prefill, cu_seqlens_q, ...)

def reset_context():                                     # gọi ở cuối run
    global _CONTEXT
    _CONTEXT = Context()
```

`max_seqlen_q` / `max_seqlen_k` là độ dài chuỗi dài nhất trong batch mà `flash_attn_varlen_func` cần, dùng kèm `cu_seqlens`. Decode chỉ đặt ba mục `slot_mapping`, `context_lens`, `block_tables`.

💡 **Gợi ý**: đây là cách đổi biến toàn cục lấy chữ ký gọi sạch hơn. `Qwen3.forward` chỉ còn `input_ids` và `positions`; cái giá là toán tử phụ thuộc ngầm vào trạng thái toàn cục, nên mỗi lần `forward` phải `set_context` trước. Vòng suy luận của nano-vllm chạy tuần tự một luồng, mỗi rank một tiến trình, nên tiền đề đó đúng. Cuối `run`, `reset_context` bỏ tham chiếu để tensor bước này không bị bước sau dùng nhầm.

## 4. Bộ nhớ GPU của KV Cache được cắt thế nào

Bộ nhớ GPU vật lý mà `slot_mapping` ở mục 2 trỏ tới được cấp một lần lúc engine khởi động. `ModelRunner` không dành sẵn theo độ dài tối đa cho mỗi request. Nó **nạp trọng số trước, dùng warmup đo đỉnh kích hoạt, rồi cắt hết bộ nhớ còn lại thành khối KV**. Đó là lý do ở 3.2 `num_kvcache_blocks` ban đầu là `-1` và chỉ tính lúc chạy.

Warmup chạy một lần prefill kích thước tối đa trên một batch chuỗi giả:

```python
def warmup_model(self):
    torch.cuda.empty_cache()
    torch.cuda.reset_peak_memory_stats()              # thống kê đỉnh bắt đầu lại từ đây
    seq_len = min(max_num_batched_tokens, max_model_len)
    num_seqs = min(max_num_batched_tokens // seq_len, max_num_seqs)
    seqs = [Sequence([0] * seq_len) for _ in range(num_seqs)]   # chuỗi giả không có block_table
    for seq in seqs:
        seq.num_scheduled_tokens = seq_len
    self.run(seqs, True)
    torch.cuda.empty_cache()
```

Cấu hình mặc định là `16384 // 4096 = 4` chuỗi 4096 token, đúng bằng token budget một bước. Lúc này KV Cache chưa cấp, `k_cache.numel()` bằng 0, nhánh ghi Cache của Attention ở 3.3 bị bỏ qua, đỉnh đo được chỉ gồm trọng số và kích hoạt. Sau đó `allocate_kv_cache` cắt khối theo phần dư:

```python
def allocate_kv_cache(self):
    free, total = torch.cuda.mem_get_info()
    used = total - free                                                # bộ nhớ cả card đã chiếm
    peak = torch.cuda.memory_stats()["allocated_bytes.all.peak"]      # đỉnh cấp phát trong warmup
    current = torch.cuda.memory_stats()["allocated_bytes.all.current"]
    num_kv_heads = hf_config.num_key_value_heads // self.world_size    # số đầu KV rank này phụ trách
    block_bytes = 2 * num_layers * block_size * num_kv_heads * head_dim * dtype.itemsize
    config.num_kvcache_blocks = int(total * gpu_memory_utilization - used - peak + current) // block_bytes
    assert config.num_kvcache_blocks > 0
    # một tensor 6 chiều chứa K và V của mọi lớp, mọi khối
    self.kv_cache = torch.empty(2, num_layers, num_kvcache_blocks, block_size, num_kv_heads, head_dim)
    layer_id = 0
    for module in self.model.modules():                # gắn lần lượt vào Attention mỗi lớp
        if hasattr(module, "k_cache") and hasattr(module, "v_cache"):
            module.k_cache = self.kv_cache[0, layer_id]
            module.v_cache = self.kv_cache[1, layer_id]
            layer_id += 1
```

Công thức số khối:

$$
\text{num\_blocks} = \left\lfloor \frac{\text{total} \times \text{util} - \text{used} - (\text{peak} - \text{current})}{\text{block\_bytes}} \right\rfloor
$$

`used` là mức chiếm cả card mà driver thấy: trọng số, CUDA context, caching allocator của PyTorch, cả phần tiến trình khác trên cùng GPU. `peak - current` là phần kích hoạt chiếm nhiều hơn hiện tại trong warmup; lúc chạy thật đỉnh đó sẽ xuất hiện lại nên phải chừa trước. Số byte mỗi khối:

$$
\text{block\_bytes} = 2 \times L \times \text{block\_size} \times \frac{H_{kv}}{\text{tp}} \times d_{\text{head}} \times \text{itemsize}
$$

Lấy Qwen3-0.6B làm ví dụ (28 lớp, 8 đầu KV, `head_dim = 128`, bf16, TP=1): $2 \times 28 \times 256 \times 8 \times 128 \times 2 = 29{,}360{,}128$ byte, tức 28 MiB mỗi khối và 112 KiB mỗi token. Khoảng 1 GiB bộ nhớ GPU chứa được khoảng 36 khối, khoảng 9200 token.

📌 **Điểm then chốt**: KV Cache là một **tensor 6 chiều** `(2, số lớp, số khối, kích thước khối, số đầu KV, head_dim)`, chiều 0 tách K và V. Sau khi cấp phát, lát cắt mỗi lớp được gắn vào thuộc tính `k_cache` / `v_cache` của Attention tương ứng; `store_kvcache` và `flash_attn_with_kvcache` ở 3.3 đọc ghi thẳng `self.k_cache`. Phần bộ nhớ còn lại cắt hết thành khối KV, không dành sẵn theo request; số chuỗi chứa đồng thời phụ thuộc độ dài thực tế.

⚠️ **Lưu ý**: dtype của KV Cache khớp dtype mặc định của mô hình (trong `__init__` đặt thành `hf_config.dtype`). nano-vllm không hiện thực lượng tử hóa KV Cache.

## 5. CUDA Graph: chỉ tăng tốc decode

Ở decode mỗi bước mỗi chuỗi chỉ tính một token, lượng tính của một kernel rất nhỏ, nên **chi phí CPU lần lượt launch kernel (launch overhead) chiếm tỷ lệ lớn hơn**: GPU xong một kernel nhỏ rồi phải chờ CPU gửi kernel tiếp. CUDA Graph ghi chuỗi launch thành một đồ thị; sau đó một lần `replay()` phát lại cả chuỗi, bỏ chi phí launch từng cái trên CPU.

CUDA Graph ghi lại kernel và **địa chỉ GPU cố định** mà chúng đọc ghi. Khi replay chỉ đổi được dữ liệu, không đổi địa chỉ hay hình dạng. Vì vậy nano-vllm cấp trước một bộ buffer tĩnh theo batch tối đa, cho Context trỏ vào lát cắt của các buffer đó, rồi capture một đồ thị cho mỗi bậc batch:

```python
@torch.inference_mode()
def capture_cudagraph(self):
    max_bs = min(self.config.max_num_seqs, 512)
    max_num_blocks = (config.max_model_len + self.block_size - 1) // self.block_size
    input_ids = torch.zeros(max_bs, dtype=torch.int64)       # buffer tĩnh, mọi đồ thị dùng chung
    positions = torch.zeros(max_bs, dtype=torch.int64)
    slot_mapping = torch.zeros(max_bs, dtype=torch.int32)
    context_lens = torch.zeros(max_bs, dtype=torch.int32)
    block_tables = torch.zeros(max_bs, max_num_blocks, dtype=torch.int32)
    outputs = torch.zeros(max_bs, hf_config.hidden_size)
    self.graph_bs = [1, 2, 4, 8] + list(range(16, max_bs + 1, 16))
    self.graphs, self.graph_pool = {}, None
    for bs in reversed(self.graph_bs):                       # capture từ lớn đến nhỏ
        graph = torch.cuda.CUDAGraph()
        set_context(False, slot_mapping=slot_mapping[:bs], context_lens=context_lens[:bs],
                    block_tables=block_tables[:bs])
        outputs[:bs] = self.model(input_ids[:bs], positions[:bs])    # chạy bình thường một lần trước
        with torch.cuda.graph(graph, self.graph_pool):
            outputs[:bs] = self.model(input_ids[:bs], positions[:bs])    # rồi mới capture
        if self.graph_pool is None:
            self.graph_pool = graph.pool()                   # pool bộ nhớ của đồ thị lớn nhất cho các đồ thị sau dùng chung
        self.graphs[bs] = graph
        torch.cuda.synchronize()
        reset_context()
    self.graph_vars = dict(input_ids=input_ids, positions=positions, slot_mapping=slot_mapping,
                           context_lens=context_lens, block_tables=block_tables, outputs=outputs)
```

- 🔑 **Bậc**: mặc định `max_num_seqs = 512` thì bậc là 1, 2, 4, 8 và từ 16 đến 512 mỗi 16 một bậc, tổng 36 đồ thị.
- **Capture từ lớn đến nhỏ**: đồ thị đầu (lớn nhất) cấp pool bộ nhớ, truyền qua `graph.pool()` cho các đồ thị nhỏ sau dùng lại, nên 36 đồ thị không mỗi cái một phần kích hoạt trung gian.
- **Chạy một lần trước khi capture**: toán tử có `@torch.compile` có thể biên dịch lại khi gặp hình dạng đầu vào mới, Triton kernel cũng JIT lần gọi đầu; những việc đó không được xảy ra trong lúc capture.
- Đồ thị chỉ đến hidden state; `compute_logits` và sampling chạy ngoài đồ thị (mục 8 của 3.3).

Lúc chạy, chọn đồ thị không nhỏ hơn batch thực tế, copy dữ liệu vào buffer tĩnh rồi replay:

```python
@torch.inference_mode()
def run_model(self, input_ids, positions, is_prefill):
    if is_prefill or self.enforce_eager or input_ids.size(0) > 512:
        return self.model.compute_logits(self.model(input_ids, positions))  # eager
    bs = input_ids.size(0)
    context = get_context()
    graph = self.graphs[next(x for x in self.graph_bs if x >= bs)]   # làm tròn lên bậc
    graph_vars = self.graph_vars
    graph_vars["input_ids"][:bs] = input_ids
    graph_vars["positions"][:bs] = positions
    graph_vars["slot_mapping"].fill_(-1)                  # vị trí pad: slot = -1, không ghi Cache
    graph_vars["slot_mapping"][:bs] = context.slot_mapping
    graph_vars["context_lens"].zero_()                    # vị trí pad: độ dài 0, không đọc Cache
    graph_vars["context_lens"][:bs] = context.context_lens
    graph_vars["block_tables"][:bs, :context.block_tables.size(1)] = context.block_tables
    graph.replay()
    return self.model.compute_logits(graph_vars["outputs"][:bs])
```

Hình dưới lấy ví dụ 37 chuỗi: không có bậc 37, chọn đồ thị 48 để replay, 11 vị trí thừa là pad (xanh = chuỗi thật; xám = pad):

<img src="/AIInfraGuide/images/inference-engine/nano-vllm-cudagraph-bucket.svg" alt="Bậc batch 1, 2, 4, 8, 16, 32, 48 đến 512; 37 chuỗi làm tròn lên bậc 48; 37 hàng đầu copy dữ liệu thật, 11 hàng sau slot_mapping=-1 và context_lens=0; sau replay chỉ lấy 37 hàng đầu của outputs" style="max-width: 100%; display: block; margin: 0 auto;" />

- 🔑 **Chỉ capture decode**: tổng số token mỗi bước prefill luôn đổi, không dùng được đồ thị hình dạng cố định; decode mỗi chuỗi luôn 1 token, chỉ kích thước batch đổi, capture trước vài chục bậc là phủ được.
- 🔑 **Xử lý vị trí pad thế nào**: `slot_mapping` điền -1, `store_kvcache` ở 3.3 gặp -1 thì return ngay, không ghi Cache; `context_lens` điền 0 nên attention không đọc lịch sử nào. `input_ids` / `positions` ở chỗ pad giữ giá trị cũ lần trước; kết quả tính ra bị bỏ khi cắt `outputs[:bs]`. `block_tables` chỉ ghi đè `bs` hàng đầu và vài cột đầu; chỉ số khối cũ còn sót cũng không bị đọc vì `context_lens` giới hạn.
- **`enforce_eager=True`**: `run_model` luôn đi nhánh eager, lúc khởi động cũng không capture đồ thị. Bật khi debug để mỗi kernel thật sự launch, dễ lần ra lỗi; tắt khi đo throughput.
- **Batch vượt 512 thì về eager**: bậc tối đa 512; nếu `max_num_seqs` đặt lớn hơn, phần vượt chạy bình thường.

⚠️ **Lưu ý**: khi `max_num_seqs` nhỏ hơn 512 và không phải bội của 16 (và lớn hơn 8), bậc lớn nhất nhỏ hơn `max_num_seqs`. Ví dụ đặt 100 thì bậc lớn nhất là 96; batch 97–100 khiến `next(...)` không tìm được bậc và ném `StopIteration`. Dùng mặc định 512 thì không gặp.

## 6. Phối hợp tiến trình dưới tensor parallelism

Mục 3.2 đã nói `LLMEngine` dùng `spawn` khởi động tiến trình con worker cho `rank>0`, và trong đó cũng chạy `ModelRunner`. Việc gom tensor đi NCCL (`init_process_group("nccl", "tcp://localhost:2333", ...)`). "Bước này phải làm gì" do rank 0 phát qua một vùng shared memory, thành một RPC rất nhỏ:

```python
def write_shm(self, method_name, *args):        # rank 0
    data = pickle.dumps([method_name, *args])
    n = len(data)
    self.shm.buf[0:4] = n.to_bytes(4, "little") # 4 byte đầu ghi độ dài
    self.shm.buf[4:n+4] = data
    for event in self.event:                    # rank 0 giữ Event của mọi worker
        event.set()

def read_shm(self):                             # rank > 0
    self.event.wait()
    n = int.from_bytes(self.shm.buf[0:4], "little")
    method_name, *args = pickle.loads(self.shm.buf[4:n+4])
    self.event.clear()
    return method_name, args

def call(self, method_name, *args):
    if self.world_size > 1 and self.rank == 0:
        self.write_shm(method_name, *args)      # phát cho worker trước
    return getattr(self, method_name)(*args)    # rồi tự chạy

def loop(self):                                 # rank > 0 vào cuối __init__ và không quay lại
    while True:
        method_name, args = self.read_shm()
        self.call(method_name, *args)
        if method_name == "exit":
            break
```

- Shared memory tên `"nanovllm"`, kích thước `2**20` byte (1 MiB), do rank 0 tạo; sau `dist.barrier()` worker mở theo tên.
- Mỗi bước ghi vào là tên phương thức và list `Sequence` đã pickle. `Sequence.__getstate__` ở decode chỉ đóng gói vài số nguyên, `block_table` và `last_token` (mục 3.1 của 3.4), nên thông điệp mỗi bước rất nhỏ.
- Địa chỉ khởi tạo NCCL và tên shared memory đều hard-code. Ngay cả TP=1 cũng khởi tạo process group trên cổng 2333, nên hai instance nano-vllm trên cùng máy sẽ đụng cổng; TP>1 thì tên shared memory cũng đụng.

📌 **Điểm then chốt**: rank 0 phụ trách lập lịch, sampling, giữ tokenizer; rank 1 đến N-1 chỉ chạy forward trên phần trọng số của mình và gom kết quả với rank 0 qua `all_reduce` / `gather` đã nói ở 3.3. Một lối vào `call("run", seqs, is_prefill)` mà `step` gọi ở 3.2 khiến mọi rank chạy cùng một bước.

## 7. Benchmark và so với vLLM

README của nano-vllm đưa một bộ so sánh throughput với vLLM (số liệu lấy từ README commit ngày 2026-04-26):

| 📊 Mục | Cấu hình |
|---------|------|
| Phần cứng | RTX 4070 Laptop (8GB bộ nhớ GPU) |
| Mô hình | `Qwen3-0.6B` |
| Số request | 256 chuỗi |
| Độ dài vào/ra | mỗi bên ngẫu nhiên trong 100–1024 token |

| Engine | Tổng token ra | Thời gian | Throughput |
|------|-------------|------|------|
| vLLM | 133,966 | 98.37 s | 1361.84 tok/s |
| **nano-vllm** | 133,966 | **93.41 s** | **1434.13 tok/s** |

Trước khi đọc các số đó, xem `bench.py` đo thế nào:

- `seed(0)` cố định số ngẫu nhiên; prompt là token id ngẫu nhiên từ `randint(0, 10000)`, độ dài `randint(100, 1024)`; `max_tokens` của mỗi chuỗi lấy `randint(100, 1024)`.
- `ignore_eos=True`, `temperature=0.6`, bảo đảm mỗi chuỗi sinh đủ `max_tokens`, tổng token ra của hai engine giống nhau.
- `LLM(path, enforce_eager=False, max_model_len=4096)` bật CUDA Graph; trước khi bấm giờ chính thức dùng một request ngắn để warmup.
- Throughput = `sum(max_tokens) / tổng_thời_gian`. Tử số chỉ đếm token ra, mẫu số lại gồm cả thời gian prefill. Đây là throughput đầu ra end-to-end, không phải throughput decode.
- README không ghi phiên bản vLLM dùng để so.

💡 **Gợi ý**: bộ kết quả này nói rằng trên một GPU, mô hình nhỏ 0.6B, sinh offline theo batch, throughput của nano-vllm ngang tầm vLLM, cao hơn khoảng 5%. Nó không nói nano-vllm cũng nhanh hơn trên mô hình lớn, ngữ cảnh dài, phục vụ online hay nhiều GPU. Ở những kịch bản đó, mixed batching, nhiều Attention backend và hỗ trợ lượng tử hóa của vLLM đều có tác dụng, và benchmark này không phủ. Cách nói chính xác hơn: nano-vllm dùng khoảng 1200 dòng hiện thực các cơ chế chính PagedAttention, prefix cache, continuous batching, CUDA Graph, và trong bài test này đạt throughput ngang vLLM.

Nối sáu mục của cả chương, chuỗi gọi đầy đủ của một `step` như dưới đây. Chữ xanh góc trên trái mỗi khung là mục giải thích nó:

## 📝 Tóm tắt

- Luồng `ModelRunner.run`: tensor hóa chuỗi và `set_context` → `run_model` (eager hoặc replay CUDA Graph) → `compute_logits` → rank 0 sample → `reset_context`.
- Prefill ghép chuỗi độ dài khác nhau nối đuôi nhau; phía Q chỉ đặt token tính vòng này, dùng `cu_seqlens_q` / `cu_seqlens_k` đánh biên; khi K dài hơn Q (trúng prefix hoặc tiếp tục chunked) mới mang `block_tables`. Decode mỗi chuỗi chỉ đưa `last_token`, dùng `context_lens` và `block_tables` đọc lịch sử từ Cache. Cả hai giai đoạn `slot_mapping` ghi K/V mới vào `chỉ_số_khối_vật_lý × block_size + lệch_trong_khối`.
- `Context` toàn cục để toán tử lấy các tensor đó qua `get_context()`, chữ ký `forward` chỉ còn `input_ids` và `positions`; cái giá là mỗi bước phải `set_context` trước.
- Lúc khởi động chạy một lần prefill kích thước tối đa (mặc định 4 × 4096 token) đo đỉnh kích hoạt, rồi cắt bộ nhớ còn lại thành khối KV theo `total × util − used − (peak − current)`. KV Cache là tensor 6 chiều `(2, lớp, khối, kích thước khối, đầu KV, head_dim)`, cắt theo lớp gắn vào mỗi Attention. Qwen3-0.6B mỗi khối 28 MiB, mỗi token 112 KiB.
- CUDA Graph chỉ capture decode: mặc định 36 bậc batch capture từ lớn đến nhỏ, dùng chung một pool bộ nhớ; lúc chạy làm tròn lên bậc, chỗ pad `slot_mapping` điền -1, `context_lens` điền 0. Khi `max_num_seqs` không phải bội của 16, batch trên bậc lớn nhất sẽ ném `StopIteration`.
- Dưới tensor parallelism, rank 0 ghi tên phương thức và `Sequence` đã pickle vào 1 MiB shared memory, dùng Event báo worker chạy cùng phương thức; gom tensor đi NCCL. Cổng 2333 và tên shared memory đều hard-code.
- Trong benchmark README (RTX 4070 Laptop, Qwen3-0.6B, 256 request ngẫu nhiên) throughput đầu ra end-to-end của nano-vllm cao hơn vLLM khoảng 5%. Điều đó chỉ nói hai bên ngang nhau ở kịch bản một GPU, mô hình nhỏ, sinh offline theo batch.

- Nói được năm bước của `ModelRunner.run`, và bước nào chỉ chạy ở rank 0

- Giải thích được vì sao `context_lens` của decode gồm cả token mới, và `-1` pad của `block_tables` khác `-1` của `slot_mapping` thế nào

- Nói rõ vì sao warmup phải chạy trước khi cấp KV Cache, và dùng công thức tính số byte mỗi khối KV của Qwen3-0.6B
- Giải thích được vì sao CUDA Graph chỉ capture decode, vì sao capture từ lớn đến nhỏ, và chỗ pad vì sao không ghi hỏng Cache
- Đưa được ví dụ giá trị `max_num_seqs` khiến `run_model` ném `StopIteration`
- Mô tả được dưới tensor parallelism rank 0 dùng shared memory và Event thế nào để worker chạy cùng một bước
